# SpeakEasy — архитектура скелета (Этап 0), 23.08.2026

Статус: **обязательная к исполнению спецификация**. Пять агентов-строителей (`scaffold`, `backend`, `agent`, `web`, `docs`) реализуют её параллельно, не общаясь между собой. Наборы файлов у владельцев **не пересекаются**.

Цель Этапа 0 — доказать, что разговор RU↔HE ощущается естественным. Двое тестеров. Клиент — веб. Всё должно **запускаться на 8 GB M1 без ключей, без Docker, без GPU** (mock-провайдеры), а реальные провайдеры включаться одним `.env`.

Связанные документы: [00-concept.md](00-concept.md), [01-assessment-claude.md](01-assessment-claude.md), [02-infrastructure.md](02-infrastructure.md), [subtitles-ux.md](subtitles-ux.md), [04-runbook.md](04-runbook.md), [05-providers.md](05-providers.md).

## 1. Решения и обоснования

### 1.1 Одна комната + выборочная подписка (НЕ две мостовые комнаты)

**Решение:** одна LiveKit-комната `call-<callId>`. Оба человека и (в TRANSLATED) агент — в ней.

Обоснование:
- Количество медиа-хопов одинаково в обоих вариантах (`человек → SFU → агент → SFU → человек`), то есть две комнаты **не дают выигрыша по задержке** — только сложность.
- Две комнаты делают DIRECT **невозможным**: «языки совпали → чистый WebRTC» требует, чтобы A и B были в одной комнате. Переключение DIRECT↔TRANSLATED превратилось бы в миграцию между комнатами вместо переключения подписки.
- Две комнаты убивают взаимное presence (mute, качество связи, список участников).
- Механизм двух комнат существует (LiveKit сам делает это в `beta/workflows/warm_transfer.py`), но нужен только при криптографической изоляции сырого аудио между людьми. Нам это не нужно.

Как B слышит только иврит — **три слоя**, реализуем первый и второй:

1. **Клиент** (наш код): `room.connect(url, token, { autoSubscribe: false })`, затем подписка только на нужную публикацию. Это же — переключатель режима: одно сигнальное сообщение.
2. **Агент, серверное принуждение**: `local_participant.set_track_subscription_permissions(allow_all_participants=False, participant_permissions=[...])` — вызывается **после** обеих публикаций. Кривой клиент не сможет услышать не тот язык.
3. (Не в Этапе 0) серверный `update_subscriptions` из бэкенда.

### 1.2 Низкоуровневые rtc-примитивы, НЕ `AgentSession`

`AgentSession` — однонаправленный turn-taking пайплайн: он привязан ровно к одному участнику (`RoomOptions.participant_identity`) и владеет ровно одним аудиовыходом. Симметричное реле — это два независимых, одновременно активных направления. Официальный `examples/other/translation/multi-user-translator.py` тоже обходит `AgentSession` и работает на примитивах.

Используем: `rtc.AudioStream.from_track`, `rtc.AudioSource`, `rtc.LocalAudioTrack.create_audio_track`, `publish_track`, `rtc.AudioResampler`, `local_participant.stream_text`, `set_track_subscription_permissions`, плюс `stt.STT.stream()` / `tts.TTS.synthesize()` из плагинов.

**Приватные API не используем.** В официальном примере задействованы `voice._ParticipantAudioOutput`, `voice._ParticipantStreamTranscriptionOutput`, `voice.TranscriptSynchronizer` — они с подчёркиванием и могут сломаться в любом патче 1.7.x. Мы платим за это чуть менее точной синхронизацией субтитров с аудио и получаем стабильность.

### 1.3 Агент — самостоятельный процесс, а не `AgentServer` worker

**Решение:** агент — обычная asyncio-программа: маленький aiohttp-сервер (`POST /jobs`) + `rtc.Room()`, подключаемая токеном, который выпускает бэкенд.

Обоснование — это прямое следствие продуктового принципа *AI is not in the call path unless it is needed*:
- При автоматическом dispatch воркер LiveKit заходит **в каждую комнату**. Для DIRECT это нарушение принципа на уровне архитектуры, а не настройки.
- Явный dispatch (`agent_name=` + серверный AgentDispatch API) решил бы это, но добавляет непроверенную поверхность API в Node SDK и завязывает нас на семантику dispatch.
- Свой процесс даёт **структурную гарантию**: в DIRECT агент вообще не имеет соединения с LiveKit. Это проверяется одним `GET /healthz` → `activeCalls: 0`.
- Паттерн «свой `rtc.Room()` + свой токен» — официальный, LiveKit применяет его сам в `warm_transfer.py`.
- Мы теряем job lifecycle, load balancing и prewarm — для двух тестеров это не имеет значения.

Миграция на `AgentServer` + explicit dispatch — задача Этапа 1, когда появится больше одного одновременного звонка.

### 1.4 Провайдеры Этапа 0

| Стадия | `mock` (по умолчанию) | `api` (Этап 0) | `runpod` |
|---|---|---|---|
| STT | детерминированный скрипт фраз | **Deepgram Nova-3** (`he`/`ru`, streaming) | заглушка |
| MT | словарь фикстур | **Gemini 3.5 Flash-Lite** (REST) | заглушка |
| TTS | речеподобный синтез из тонов | **Cartesia Sonic 3.5** (pinned snapshot) | заглушка |

Почему так:

- **STT = Deepgram Nova-3.** Иврит и русский оба в streaming, плагин `livekit-plugins-deepgram==1.7.0` проверен на PyPI, зависимости резолвятся. По независимому ивритскому лидерборду (ivrit.ai) Nova-3 даёт WER 6.7% на разговорном eval-d1 — второе место среди облачных стриминговых движков. **Soniox `stt-rt-v5` объективно лучше** (4.8% eval-d1, 9.0% WhatsApp, нативный code-switching, $0.12–0.18/час), но версия его LiveKit-плагина в линейке 1.7.0 не подтверждена. Soniox — первый апгрейд после того, как скелет заведётся: это ровно один новый файл `providers/stt_soniox.py` + одна строка в реестре.
- **MT = Gemini 3.5 Flash-Lite через сырой REST** (`aiohttp`, без SDK). Единственный класс систем, которому можно **сообщить пол говорящего, пол слушающего и регистр ты/вы** — а для RU↔HE это не вопрос качества, это вопрос грамматичности. TTFT ~0.29 s на 10k-нагрузке, у нас промпт ~450 токенов. ~$0.0029 за переведённую минуту — в 3–8 раз дешевле посимвольных MT-API, которые при этом не умеют род.
- **TTS = Cartesia Sonic 3.5**, id закреплён снапшотом `sonic-3.5-2026-05-04`. Единственный вендор с **одной и той же** низколатентной моделью для `he` и `ru` (sub-90 ms заявлено), плагин `livekit-plugins-cartesia==1.7.0` проверен. Резерв — Google Chirp 3 HD (`he-IL` GA, 1M символов/мес бесплатно, streaming TTFB ~200 ms).

Запрещено (проверено исследованием, ошибка стоит дней отладки):
- `eleven_flash_v2_5`, `eleven_multilingual_v2`, `eleven_turbo_v2_5` — **иврита нет**. Иврит только в `eleven_v3` (без стриминга) и `eleven_v3_conversational` (~280 ms).
- Deepgram **Flux** — ни иврита, ни русского.
- AssemblyAI как единственный вендор — в streaming нет русского.
- Amazon Polly — иврита нет вовсе.
- XTTS-v2 / Piper / Kokoro — иврита нет. Строка про XTTS-v2 в [02-infrastructure.md](02-infrastructure.md) для иврита неверна.
- `livekit.agents.inference.STT/LLM/TTS` — они ходят в `agent-gateway.livekit.cloud`, против self-hosted сервера не работают.

Никакого диакритизатора (Nakdan/Phonikud) в пайплайне Этапа 0: все три рекомендованных TTS — контекстные модели, они снимают неоднозначность огласовок сами. Точечные исправления произношения — маленькая карта переопределений (никуд прямо в тексте), не общий G2P.

### 1.5 LiveKit: локально по умолчанию, Cloud — сменой трёх переменных

`livekit-server 1.13.5` уже стоит через Homebrew (`/opt/homebrew/bin/livekit-server`). Комитим `livekit.yaml`, запускаем `livekit-server --config livekit.yaml`.

Cloud (бесплатный tier Build: 5 одновременных соединений, 5 000 WebRTC-минут/мес, карта не нужна) включается сменой `LIVEKIT_URL` / `LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET`. Код минтинга токенов и клиентский код **байт-в-байт одинаковы**. Стоимость поддержки обоих путей — ноль, поэтому поддерживаем оба с первого коммита.

Важно про удалённого тестера: **туннели (ngrok/cloudflared) не переносят WebRTC-медиа**. Комната соединится, звука не будет — самый обманчивый режим отказа во всём стеке. Для тестера из другой страны есть ровно два пути: LiveKit Cloud (рекомендуется) или UDP-mesh (Tailscale + `tailscale cert`). На туннели не тратить ни часа.

## 2. Конечный автомат звонка

### 2.1 Режимы

- **DIRECT** — языки совпали. Чистый WebRTC. Агент не запускается, не подключается, не существует для этого звонка.
- **TRANSLATED** — языки разные. Агент в комнате, реле работает.
- **FORCED** — пользователь вручную включил перевод при совпавших языках. Медиа-путь идентичен TRANSLATED; отличие только в происхождении решения и в UI.

### 2.2 Где принимается решение

**Только в бэкенде, в момент `POST /api/calls`.** Ни клиент, ни агент режим не выбирают.

Причины: только бэкенд знает профили обоих; клиент на момент запроса не знает языка собеседника; агент в DIRECT обязан не существовать, значит он не может участвовать в решении о собственном существовании.

```
mode(callerId, calleeId, force):
    langA = effectiveLang(caller,  contactOf(caller  → callee))
    langB = effectiveLang(callee,  contactOf(callee  → caller))
    if force            -> FORCED     (reason: forced_by_user)
    if langA == langB   -> DIRECT     (reason: languages_match)
    else                -> TRANSLATED (reason: languages_differ)
```

`effectiveLang` = переопределение в карточке контакта, иначе `lang` из профиля пользователя. Это и есть «язык — свойство контакта».

### 2.3 Как решение доводится до всех

| Кому | Как | Когда |
|---|---|---|
| Инициатору | поле `call.mode` в ответе `POST /api/calls` | сразу |
| Обоим клиентам | поле `mode` в ответе `POST /api/calls/:id/join` (в том же ответе, что и токен) | при входе |
| Агенту | `POST http://agent:8788/jobs` из бэкенда, **только если `mode != DIRECT`** | сразу после создания звонка |
| Клиентам (готовность реле) | текстовый стрим агента, топик `speakeasy.state`, `event: "agent_ready"` | когда агент опубликовал обе дорожки |

Вторая линия обороны: агент **сам отказывается** от джоба с `mode: "DIRECT"` → `400 {"accepted": false, "reason": "direct_mode_no_agent"}`.

### 2.4 Жизненный цикл

```
created ──(первый join)──► active ──(POST /end или оба ушли)──► ended
   │
   └──(POST /mode, только пока state == "created")──► created (режим пересчитан)
```

Смена режима на живом звонке в Этапе 0 запрещена: `409 mode_locked`. Механика для этого (переключение `setSubscribed`) уже есть в клиенте, но включение её на живом звонке требует согласованной остановки агента и не входит в скелет.

### 2.5 Деградация

Если агент недоступен, а режим TRANSLATED — бэкенд логирует, ставит `call.agent.dispatched = false`, звонок продолжается. Клиенты видят отсутствие `agent_ready` и показывают явный баннер «перевод недоступен». Молчаливого отката на слышимость сырого аудио собеседника **нет**: подписка на его микрофон в TRANSLATED не делается.

## 3. Потоки данных

### 3.1 DIRECT — AI вне пути

```
  Браузер A (ru)                    livekit-server (SFU)                Браузер B (ru)
  ┌──────────┐                      ┌──────────────────┐               ┌──────────┐
  │ mic ─────┼─── publish mic ─────►│  room            │               │          │
  │          │                      │  call-c_XXXX     │──► sub mic A ─┼──► speaker
  │ speaker ◄┼──── sub mic B ◄──────│                  │◄── publish ───┼─── mic
  └──────────┘                      └──────────────────┘               └──────────┘
                                    (участников: 2)

  Агента НЕТ:  бэкенд не отправлял POST /jobs
               agent:8788 /healthz -> {"activeCalls": 0}
               в комнате нет identity "agent-relay"

  Клиент: connect(autoSubscribe:false) -> subscribe(pub) если
          pub.source == Microphone && participant.identity == peerUserId
```

### 3.2 TRANSLATED / FORCED

```
 Браузер A (ru, m)                       livekit-server                    Браузер B (he, f)
 ┌────────────┐                        ┌──────────────┐                   ┌────────────┐
 │ mic ───────┼── publish "mic" ──────►│              │                   │        mic ┼──┐
 │            │                        │  room        │                   │            │  │
 │ speaker ◄──┼── sub "tx-u_alex" ◄────│ call-c_XXXX  │─── sub "tx-u_noa"─┼──► speaker │  │
 │ субтитры ◄─┼── speakeasy.subtitle ◄─│              │──speakeasy.subtitle┼─► субтитры │  │
 └────────────┘                        └──────┬───────┘                   └────────────┘  │
        A НЕ подписан на mic B                │  ▲                    B НЕ подписан на mic A
                                              │  │                                        │
                          sub mic A, mic B ───┘  └─── publish "tx-u_alex", "tx-u_noa" ◄────┘
                                              │
                                       ┌──────┴────────────────────────────────────────┐
                                       │  agent  (identity "agent-relay")              │
                                       │                                               │
                                       │  Direction A→B  (speaker=A ru m, listener=B he f)
                                       │  AudioStream(mic A,16k) → SttProvider          │
                                       │        ↓ speech_start / partial / final        │
                                       │  Chunker (LocalAgreement-2 + commit policy)    │
                                       │        ↓ committed unit                        │
                                       │  MtProvider(text, src=ru,dst=he,               │
                                       │             speaker.gender=m, listener.gender=f,│
                                       │             tone, history[4])                  │
                                       │        ↓                                       │
                                       │  TtsProvider(he) → chunks → AudioResampler→48k │
                                       │        ↓ AudioByteStream(10ms)                 │
                                       │  AudioSource(48k,1,queue_size_ms=200)          │
                                       │        ↓ track name "tx-u_noa"                 │
                                       │                                               │
                                       │  Direction B→A  — зеркально, "tx-u_alex"       │
                                       │                                               │
                                       │  Barge-in: speech_start от слушателя →         │
                                       │    cancel(mt/tts task) + source.clear_queue()  │
                                       │                                               │
                                       │  После обеих публикаций:                       │
                                       │    set_track_subscription_permissions(...)     │
                                       └───────────────────────────────────────────────┘
```

Порядок операций агента (важен):
1. `room.connect(url, token, rtc.RoomOptions(auto_subscribe=True))`. Агент в комнате есть только в TRANSLATED/FORCED, и там ему нужны оба микрофона, так что автоподписка — ровно то, что надо; выборочная подписка нужна людям, а не агенту. (У людей — наоборот: `autoSubscribe: false` и ручной `setSubscribed`.)
2. Создать `AudioSource(48000, 1, queue_size_ms=200)` × 2, опубликовать треки `tx-<listener>` с **пустым** `rtc.TrackPublishOptions()` (source не объявляем — два трека с `SOURCE_MICROPHONE` от одного участника не проверены).
3. Вызвать `set_track_subscription_permissions` — **после** обеих публикаций. Любая новая публикация после перехода в track-level режим не даёт прав никому, пока не вызвать заново.
4. Отправить `speakeasy.state` / `agent_ready`.
5. Запустить два Direction.

## 4. Бюджет задержки

| Стадия | DIRECT | TRANSLATED, `api` | TRANSLATED, `mock` |
|---|---|---|---|
| Захват + jitter-буфер | 20–50 ms | 20–50 ms | 20–50 ms |
| SFU | 10–40 ms | 10–40 ms | 10–40 ms |
| VAD/чанкер до коммита | — | 300–600 ms | 400 ms (фикс.) |
| STT до финала | — | 150–350 ms | 0 |
| MT | — | 250–400 ms | ~5 ms |
| TTS TTFB | — | 130–210 ms | ~20 ms |
| SFU + плейаут слушателя | 10–40 ms | 80–150 ms | 80–150 ms |
| **Итого mouth-to-ear** | **40–130 ms** | **≈ 0.95–1.8 s** | **≈ 0.55–0.7 s** |

Целевой коридор из [02-infrastructure.md](02-infrastructure.md) — 1.5–2.5 s; расчёт в него укладывается, **но только** при семантическом чанкинге. Что ломает бюджет:
- Sliding-window Whisper + LocalAgreement-2 на аудио: ~2.0 s при чанках 1 s, ~3.3 s на длинной речи. Не прототипировать UX на этом.
- Reasoning-токены LLM: `thinkingLevel: "minimal"` выставляем явно.
- `AudioSource` с дефолтным `queue_size_ms=1000`: до секунды уже поставленного в очередь TTS доиграет после отмены — barge-in будет ощущаться сломанным. Всегда `queue_size_ms=200`.
- Batch-режим TTS вместо streaming (Google: ~800 ms против ~200 ms).

Метрики по стадиям пишем с первого дня: агент логирует `stt_final_ms`, `mt_ms`, `tts_ttfb_ms`, `e2e_ms` на каждый коммит — это главный KPI продукта.

## 6. Абстракция провайдеров

Один интерфейс на стадию, три реализации: `mock`, облачная и `runpod`. Выбор — через `.env`, ленивый импорт в фабрике, так что отсутствующий плагин ломает только явно выбранный путь. Облачная реализация в `.env` называется именем вендора, а не словом `api`: `STT_PROVIDER=deepgram`, `MT_PROVIDER=gemini`, `TTS_PROVIDER=cartesia` (колонка «`api`» в таблицах ниже — это тир, а не значение переменной).

**`mock` обязателен и является значением по умолчанию.** Именно он делает скелет запускаемым в день первый: детерминированный, офлайн, без ключей и GPU, с реальной временной динамикой (партиалы растут, TTS играет в реальном времени), чтобы отлаживать VAD-гейт, чанкер, отмену TTS и барж-ин бесплатно.

Полные сигнатуры — в разделе «Контракты» структурированной спецификации и в `agent/src/speakeasy_agent/providers/base.py`.

Ключевые правила:
- Провайдер объявляет свою частоту дискретизации; реле само вставляет `rtc.AudioResampler`, если она не 48 кГц.
- Отмена — через отмену asyncio-задачи плюс `AudioSource.clear_queue()`. Отдельного метода `cancel()` в интерфейсе нет.
- `SttEvent.type ∈ {speech_start, partial, final, speech_end}`. `speech_start` слушателя — сигнал барж-ина; отдельный VAD в Этапе 0 не нужен.
- `runpod`-адаптеры — файлы-заглушки, поднимающие `NotImplementedError("runpod provider is a Stage-1 stub")`. Они существуют, чтобы форма интерфейса была зафиксирована до появления GPU.

## 7. Контракты

Полные контракты (HTTP, сообщения субтитров, схема атрибутов, сигнатуры адаптеров) вынесены в поле `contracts` структурированной спецификации, которую получают строители, и продублированы в [04-runbook.md](04-runbook.md). Здесь — только инварианты, которые нельзя нарушать:

- `roomName == "call-" + callId`, `callId` матчится `^c_[0-9a-f]{12}$`.
- Идентичность участника **всегда** равна `userId` (`^u_[a-z0-9_]{1,30}$`). Идентичность агента — ровно `agent-relay`.
- Имя трека агента — ровно `tx-<listenerUserId>`. Клиент подписывается по имени трека, не по индексу.
- `identity`, `name`, `metadata`, `attributes` — параметры **конструктора** `AccessToken`, а не поля `VideoGrant`. `identity` внутри `addGrant()` молча ничего не делает.
- `toJwt()` в `livekit-server-sdk` v2 — **асинхронный**. Забытый `await` даёт токен `"[object Promise]"` и невнятную ошибку авторизации.
- В `VideoGrant` `canPublish`/`canSubscribe` задаём **явно**: если не задать ни одного, включены оба.
- Атрибуты участника — плоский `Record<string,string>`; ключи: `uid`, `name`, `lang`, `gender`, `tone`, `role`.
- Топик субтитров — наш собственный `speakeasy.subtitle`, а не `lk.transcription`. Причина: нам нужен и оригинал, и перевод в одном сообщении с адресной доставкой, а `sender_identity` в `stream_text` требует прав publish-on-behalf, которые мы не хотим выдавать. `RoomEvent.TranscriptionReceived` и `publish_transcription()` устарели — не использовать.

## 8. Субтитры

Реализуем минимум из [subtitles-ux.md](subtitles-ux.md):

- Максимум 2 строки, скользящее окно, старое уезжает вверх.
- **Уже показанный закоммиченный текст не переписывается — только дополняется.** Партиалы показываются приглушённо; в основной поток попадают только финалы.
- Перевод — крупно, оригинал — мельче и приглушённо.
- `dir` выставляется **поэлементно по языку строки** (`ru → ltr`, `he → rtl`), плюс `unicode-bidi: plaintext` на контейнере — иначе точка и вопросительный знак уезжают не на тот край. Это классический баг, который выглядит как ошибка STT.
- Минимальное время на экране ~1 s.

Логика стабилизации — чистая функция в `web/src/subtitles.ts`, покрытая юнит-тестом: она принимает поток `SubtitleMessage` и отдаёт список строк для отрисовки. Тестируется без браузера и без LiveKit.

## 9. Открытые риски

1. **Две дорожки от одного участника.** Не проверено, примет ли SFU два одновременных аудиотрека от агента, если оба объявлены `SOURCE_MICROPHONE`. Смягчение: публикуем с пустым `rtc.TrackPublishOptions()` (как в официальном примере) и различаем по `track_name`. Проверить эмпирически на первом же запуске.
2. **Track-level права подписки.** После перехода в track-level режим любая новая публикация не даёт прав никому, пока не вызвать `set_track_subscription_permissions` заново. Забытый повторный вызов = тишина без единой ошибки в логах.
3. **iOS Safari и микрофон.** `getUserMedia` требует secure context. `http://<lan-ip>:5173` его не даёт — микрофона на телефоне не будет вовсе, и это легко принять за проблему LiveKit. Самоподписанные сертификаты не работают. Пути: `localhost` на самом Mac, либо LiveKit Cloud + туннель **только для веб-страницы**, либо Tailscale с настоящим сертификатом.
4. **Mixed content.** Страница по https не может открыть `ws://`. Либо оба по TLS, либо оба нет.
5. **Cloud free tier — 5 одновременных соединений.** Двое тестеров + агент + забытая вкладка = 4. Одна лишняя вкладка упирает в лимит посреди живого теста.
6. **Качество HE→RU у выбранного MT не измерено независимо.** Прямое HE→RU — направление беднее ресурсами, чем HE→EN. Нужно A/B прямого перевода против пивота через английский на реальных транскриптах до фиксации архитектуры.
7. **Пол участников — требование схемы, а не промпта.** Без пола говорящего И слушающего корректный иврит недостижим ни одной моделью ни за какие деньги (`אתה יודע` / `את יודעת`, `אני הולך` / `אני הולכת`). Русский тоже требует пола: прошедшее время и предикативы (`я сказал/сказала`). Поле обязательно в профиле и в карточке контакта с первого коммита.
8. **Тон = обязательный грамматический выбор.** В иврите нет ты/вы, поэтому в направлении HE→RU модель обязана выбрать ты или вы из чего-то вне текста. Не передашь `tone` — модель угадает и будет плавать между ты и вы посреди разговора.
9. **Code-switching.** Израильская речь постоянно мешает иврит с английским. Deepgram Nova-3 справляется хуже Soniox; английские вставки не должны переводиться на русский, если говорящий имел в виду английское слово.
10. **`livekit-plugins-soniox` в линейке 1.7.0 не проверен.** Если резолвится — переключаемся сразу, это лучший иврит на рынке. Если нет — остаёмся на Deepgram и ждём.
11. **Агент как единая точка отказа для TRANSLATED.** Один процесс, без супервизора. Падение = звонок без перевода. Для Этапа 0 приемлемо, для Этапа 1 нужен рестарт и health-gate на стороне бэкенда.
12. **Хранилище в памяти.** Бэкенд Этапа 0 держит пользователей, контакты и звонки в памяти и сидируется двумя тестовыми аккаунтами. Рестарт = потеря состояния. Это осознанно: Postgres — Этап 1.
13. **Приватность.** Бесплатные tier'ы LLM непригодны для реального содержимого звонков. До любого трафика, кроме двух тестеров, — платный tier или Vertex, с учётом израильской Поправки 13.
