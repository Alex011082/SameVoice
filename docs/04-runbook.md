```bash
brew install livekit-cli
```

Docker **не нужен** и не используется. GPU не нужен. Ключи провайдеров для mock-режима не нужны.

Чего на macOS нет: curl-инсталлятора livekit-server (скрипт обрывается на Darwin) и darwin-бинарей в GitHub Releases. Единственный путь без Homebrew — сборка из исходников на Go. Знать об этом стоит до того, как на это заложится CI.

## 2. Первый запуск с чистого клона

```bash
# 0. одноразово: окружение
cd /Users/davidov/SpeakEasy && cp .env.example .env
npm run check:env

# 1. одноразово: установка (API-ключи не нужны, mock — значение по умолчанию)
npm run deps             # backend + web + agent, три установки одной командой

```

`node scripts/check-env.mjs` (он же `npm run check:env`) сверяет `.env` с `.env.example`, сообщает о недостающих ключах и проверяет, что у выбранных провайдеров есть нужные им ключи. Для `mock` ключи не требуются — скрипт должен пройти чисто сразу после `cp`.

Опционально, только для реальных провайдеров:

```bash
npm run deps:agent:api   # == cd agent && uv sync --extra api
```

## 3. Запуск

### 3.0 Транспортный профиль

Всё в репозитории работает в двух режимах, и переключает их **одна переменная** `SPEAKEASY_PROFILE`:

| | `local` (по умолчанию) | `cloud` |
|---|---|---|
| SFU | `livekit-server` на этом Mac, `ws://` | LiveKit Cloud, `wss://` |
| Страница | `http://localhost:5173` | публичный `https://`-origin (туннель) |
| Кому годится | две вкладки на одной машине | двое людей на двух машинах в разных сетях |
| Аккаунты | ноль | один (LiveKit Cloud) |
| `scripts/livekit.sh` | запускается | **не запускается** |

Ни строчки кода при этом не меняется: URL LiveKit и токен приезжают в браузер в ответе `POST /api/calls/:id/join`, а агенту — в теле `POST /jobs`. Профиль можно переопределить на один запуск, не трогая `.env`:

```bash
SPEAKEASY_PROFILE=cloud npm run dev      # == npm run dev:cloud
SPEAKEASY_PROFILE=cloud npm run check:env # == npm run check:env:cloud
```

Развёрнутая операционка облачного профиля — [06-two-device-session.md](06-two-device-session.md). Здесь только команды.

### 3.1 Команды

Всё сразу, один терминал, `Ctrl-C` гасит всю группу процессов:

```bash
npm run dev              # local:  livekit + backend + agent + web
npm run dev:cloud        # cloud:  backend + agent + web (локальный SFU не поднимается)
npm run tunnel           # публичный https-origin поверх Vite (отдельный терминал)
```

Либо каждый сервис в своём терминале — так удобнее читать логи агента:

```bash
npm run dev:livekit      # == bash scripts/livekit.sh   (только в local)
npm run dev:backend      # == npm --prefix backend run dev
npm run dev:agent        # == cd agent && uv run python -m speakeasy_agent.main
npm run dev:web          # == npm --prefix web run dev -- --host
```

`npm run tunnel` (`scripts/tunnel.sh`) поднимает Cloudflare quick tunnel на `http://127.0.0.1:$WEB_PORT`, печатает выданный `https://<...>.trycloudflare.com` и дальше — что с ним делать по шагам. Аккаунт Cloudflare, регистрация и согласие с условиями не нужны; `cloudflared` уже стоит (`/opt/homebrew/bin/cloudflared`). Скрипт при старте закрывает туннель, оставшийся от предыдущего убитого запуска, а при выходе гасит свой — оставленный туннель публикует dev-сервер в открытый интернет без аутентификации.

**Туннель несёт только HTTP и WebSocket** — страницу, ассеты и JSON API. WebRTC-медиа (UDP/ICE/SRTP) идёт напрямую браузер → edge LiveKit Cloud и туннеля не касается. Именно поэтому облачный профиль сочетает туннель с LiveKit Cloud, а не с локальным SFU: туннель перед локальным SFU даёт самый обманчивый отказ во всём стеке — комната соединяется, список участников заполняется, звука нет.

`livekit-server` запускаем **только** с `--config`, никогда с `--dev`. Причины:
- `--dev` слушает `127.0.0.1` и `::1`, устройства в локальной сети получат таймаут без внятной ошибки;
- `--dev` использует один UDP-mux-порт 7882 вместо документированного диапазона, и правила фаервола, скопированные из документации, окажутся не про те порты;
- наличие блока `keys:` в конфиге **подавляет** автоподстановку devkey — ключ и секрет в `livekit.yaml` и в `.env` обязаны совпадать, иначе все токены отвергаются.

### Порты

| Порт | Сервис | Назначение |
|---|---|---|
| 7880/tcp | livekit-server | HTTP API + WebSocket-сигналинг, это адрес из `LIVEKIT_URL` |
| 7881/tcp | livekit-server | ICE/TCP — резерв, когда UDP закрыт |
| 50000–50100/udp | livekit-server | ICE/UDP, собственно медиа |
| 8787/tcp | backend (Fastify) | REST API, слушает `0.0.0.0` |
| 8788/tcp | agent (aiohttp) | управляющий API джобов, слушает `127.0.0.1` |
| 5173/tcp | web (Vite) | dev-сервер, поднимается с `--host`, `strictPort` |

Порт **7882/udp не открывать** — он относится только к `--dev`.

В облачном профиле входящих портов не открывается вообще ни одного. Агент остаётся на `127.0.0.1:8788` и **никогда не туннелируется**: он сам звонит наружу в LiveKit (TCP 443 сигналинг, UDP 3478 и 50000–60000 медиа, TURN-over-TLS на 443 как резерв), а его `/jobs` защищён только общим секретом. Публичный агент — это возможность для постороннего завести ваш агент в произвольную комнату.

Занятые порты:

```bash
lsof -nP -iTCP:7880 -iTCP:8787 -iTCP:8788 -iTCP:5173 -sTCP:LISTEN
```

## 4. Проверка, что скелет живой

```bash
curl -s http://127.0.0.1:8787/healthz
curl -s http://127.0.0.1:8787/api/config
curl -s http://127.0.0.1:8788/healthz
```

Ожидаемо: у бэкенда `{"ok":true,"service":"backend",...}`, у агента `{"ok":true,"service":"agent",...,"activeCalls":0,"callIds":[]}` и провайдеры `mock/mock/mock`.

`GET /api/config` теперь отдаёт ещё и параметры звонка-вызова (`ring.timeoutSeconds`, `ring.presenceTtlSeconds`, `ring.pollIntervalMs`). `GET /healthz` агента отдаёт `evalLog: {enabled, dir}` и `failedCalls`, а `/healthz` бэкенда — `calls: {live, ended}`.

> **Звонки больше не бессмертны.** Стор бэкенда в памяти, и до 25.08.2026 звонок в нём жил, пока процесс не перезапустят — на этом провалился тест двух человек (§10 в [07-product-spec.md](07-product-spec.md)). Теперь звонок, в который никто не вошёл, завершается через **10 минут** простоя, вошедший — через **3 часа** от создания. Завершённый звонок завершён сразу; ещё 10 минут он доступен по обычному маршруту `GET /api/calls/:callId`, потом уезжает в **архив** (`CALL_ARCHIVE_DIR`, по умолчанию `logs/archive`, один JSON-файл на звонок) и читается только его участниками. Ничего не удаляется. В карте живёт не больше 500 записей: при переполнении завершённые уезжают в архив досрочно, живые не трогаются никогда. Реле агента само уходит из комнаты, простоявшей без людей 120 секунд. Если `calls.live` в `/healthz` растёт и не опускается — это ровно тот класс утечки, который эти границы обязаны ловить.

> **Точность, а не намерение.** Клиент эти три числа **не использует** — он только проверяет, что блок `ring` вообще есть, чтобы отличить свежий бэкенд от старого (`web/src/main.ts`, `state.config?.ring !== undefined`). Реальная каденция опроса — константы в `web/src/ring.ts` (1200 / 2500 / 5000 мс), и они могут молча разойтись с `PRESENCE_TTL_SECONDS` на сервере. Проверено 23.08.2026.

### 4.1 Полный список HTTP-маршрутов

**Бэкенд, `:8787`** — без аутентификации, CORS по allowlist:

| Метод | Путь | Зачем |
|---|---|---|
| `GET` | `/healthz` | жив ли + `calls: {live, ended}` — сколько звонков держит стор в памяти |
| `GET` | `/api/config` | `livekitUrl`, провайдеры, топики, параметры ринга |
| `GET` | `/api/users` · `/api/users/:userId` | сид из двух аккаунтов |
| `PATCH` | `/api/users/:userId` | профиль |
| `GET` | `/api/users/:userId/contacts` | карточки контактов |
| `GET` | `/api/users/:userId/calls` | **новое.** архив: список завершённых звонков этого участника, свежие первыми |
| `GET` | `/api/users/:userId/calls/:callId` | **новое.** архив: одна запись. Чужой звонок — `404`, а не `403`: 403 сам по себе подтвердил бы, что звонок существует |
| `PATCH` | `/api/users/:userId/contacts/:contactUserId` | `{lang,gender,tone,forceTranslate}` — переопределения |
| `POST` | `/api/presence` | **новое.** `{userId, online}` — heartbeat И опрос звонков одним ответом |
| `GET` | `/api/ring/:userId` | **новое.** тот же ответ без побочного эффекта |
| `POST` | `/api/calls` | `{callerId, calleeId, force, ring, ringTimeoutSeconds?}` → `{call, ring}` |
| `GET` | `/api/calls/:callId` | состояние звонка + вид ринга |
| `POST` | `/api/calls/:callId/join` | токен участника, `livekitUrl`, `expectedAgentTrackName` |
| `POST` | `/api/calls/:callId/mode` | пересчёт режима (только до `active`) |
| `POST` | `/api/calls/:callId/end` | завершить |
| `POST` | `/api/calls/:callId/ring/accept` | **новое.** только вызываемый |
| `POST` | `/api/calls/:callId/ring/decline` | **новое.** только вызываемый |
| `POST` | `/api/calls/:callId/ring/cancel` | **новое.** только звонящий |
| `POST` | `/api/calls/:callId/verdict` | **новое.** `{userId, verdict, utteranceId?, expected?, note?}` |

**Агент, `127.0.0.1:8788`** — всё, кроме `/healthz`, требует заголовок `x-speakeasy-agent-key`:

| Метод | Путь | Зачем |
|---|---|---|
| `GET` | `/healthz` | `activeCalls`, `callIds`, `failedCalls`, `evalLog` |
| `GET` | `/stats` | **новое.** подробный снимок джобов и отказов, включая `humans` и `emptyForS` по каждому реле |
| `POST` | `/jobs` | завести реле; на `mode: "DIRECT"` отвечает `400 direct_mode_no_agent` |
| `POST` | `/jobs/:callId/stop` | погасить |
| `POST` | `/jobs/:callId/verdict` | **новое.** вердикт судьи (так его шлёт бэкенд) |
| `POST` | `/verdicts` | **новое.** то же самое, `callId` в теле |

Ответ на вердикт — `202 {accepted, callId, utteranceId, resolved}`. `verdict` принимает `wrong` или `ok`. `utteranceId` можно не передавать — тогда агент сам возьмёт самую свежую реплику, **слушателем которой был именно этот пользователь** и у которой перевод действительно получился.

### 4.2 Переменные окружения, появившиеся в этом этапе

Все с рабочими значениями по умолчанию; `.env.example` — единственный источник правды.

| Переменная | Дефолт | Кто читает |
|---|---|---|
| `SPEAKEASY_PROFILE` | `local` | `check-env.mjs`, `dev.sh`, `tunnel.sh` |
| `PUBLIC_WEB_ORIGIN` | пусто | `dev.sh` (баннер) и `check-env.mjs` — **и больше никто** |
| `VITE_POLL_INTERVAL_MS` | `2000` | **никто** (см. ниже) |
| `PRESENCE_TTL_SECONDS` | `15` | бэкенд |
| `RING_TIMEOUT_SECONDS` | `45` | бэкенд |
| `EVAL_LOG_ENABLED` | `true` | агент |
| `EVAL_LOG_DIR` | `logs/calls` | агент, review-CLI, `dev.sh` |

Две строки в этой таблице раньше были неверны, и обе способны увести отладку не туда:

- **`PUBLIC_WEB_ORIGIN` не участвует в CORS.** Allowlist бэкенда собирается из `WEB_ORIGINS` плюс локальные origin'ы (`backend/src/config.ts`); `PUBLIC_WEB_ORIGIN` бэкенд не читает вообще. В рекомендованной схеме с одним туннелем и `VITE_BACKEND_URL=/` CORS не запускается ни разу, поэтому расхождение и не проявлялось. Если когда-нибудь поднимете API на отдельном origin — вписывать адрес надо в `WEB_ORIGINS`, а не сюда.
- **`VITE_POLL_INTERVAL_MS` не читает ни один файл** — ни TypeScript, ни Python, ни shell. Каденция браузера зашита в `web/src/ring.ts` (1200 / 2500 / 5000 мс), а число, которое бэкенд объявляет в `/api/config`, приходит из `PRESENCE_POLL_MS` (см. следующую таблицу) и клиентом игнорируется.

Шесть переменных код читает, но в `.env.example` их **нет** — они существуют для нештатных случаев, и вписывать их в `.env` без нужды не стоит (`check-env.mjs` предупредит о ключе, которого нет в примере):

| Переменная | Дефолт | Зачем |
|---|---|---|
| `WEB_ORIGINS` | пусто | доп. origin'ы для CORS через запятую; поддерживает `https://*.trycloudflare.com` |
| `ALLOW_LOCAL_ORIGINS` | `true` | оставить ли localhost/LAN в allowlist |
| `PRESENCE_POLL_MS` | `2000` | число, которое бэкенд объявляет как `ring.pollIntervalMs` в `/api/config`. Клиент его сейчас не использует |
| `DEEPGRAM_ENDPOINTING_MS` | `0` | `0` значит «следовать за `CHUNK_MAX_SILENCE_MS`» |
| `CARTESIA_API_VERSION` | пусто | переопределить `Cartesia-Version` из плагина ([05-providers.md](05-providers.md), §11) |
| `CARTESIA_SAMPLE_RATE` | `24000` | частота запроса к Cartesia до ресемплинга в 48 кГц |

При `VITE_BACKEND_URL=/` (облачный профиль) страница и API живут на одном origin, браузер CORS вообще не проверяет, и `WEB_ORIGINS` не нужен. Он понадобится только если поднимать второй туннель отдельно под бэкенд — чего делать не стоит: имена quick tunnel'ов случайны, и оба придётся переписывать при каждом рестарте.

Два тестовых аккаунта засеяны всегда:

| id | handle | язык | род | тон |
|---|---|---|---|---|
| `u_alex` | alex | ru | m | neutral |
| `u_noa` | noa | he | f | friendly |

Открыть две вкладки:

```bash
open 'http://localhost:5173/?me=u_alex'   # русский, мужской род, тон neutral
open 'http://localhost:5173/?me=u_noa'    # иврит, женский род, тон friendly
```

Каждая вкладка — отдельный «человек». Браузер спросит доступ к микрофону в обеих; на одном Mac обе вкладки будут писать один и тот же реальный микрофон — это нормально для mock-режима, где содержимое речи всё равно не анализируется.

Тесты, все офлайн и без ключей:

```bash
npm run smoke            # == bash scripts/smoke-all.sh — все три набора
npm run smoke:backend    # node --test
npm run smoke:agent      # pytest
npm run smoke:web        # vitest
```

На 24.08.2026 это 230 тестов: 49 backend, 100 agent, 81 web. Все офлайн, без ключей, без LiveKit и без сети. (Раньше здесь стояло «225: 49 / 97 / 79» — цифра отстала от репозитория; пересчитано прогоном `npm run smoke`.)

Демо пайплайна вообще без LiveKit и без сети — самый быстрый способ увидеть работу автомата состояний:

```bash
npm run demo:pipeline    # == cd agent && uv run python scripts/mock_pipeline_demo.py
```

## 5. Как убедиться, что в DIRECT агента действительно нет

Это главный продуктовый инвариант, и он проверяется, а не декларируется.

1. Сделайте языки одинаковыми — в карточке контакта у `u_alex` поставьте `he`, либо у `u_noa` — `ru`:

```bash
curl -s -X PATCH http://127.0.0.1:8787/api/users/u_alex/contacts/u_noa \
  -H 'content-type: application/json' -d '{"lang":"ru"}'
```

2. Создайте звонок и посмотрите на режим:

```bash
curl -s -X POST http://127.0.0.1:8787/api/calls \
  -H 'content-type: application/json' \
  -d '{"callerId":"u_alex","calleeId":"u_noa","force":false}'
```

Ожидается `"mode":"DIRECT"`, `"reason":"languages_match"` и `"agent":{"required":false,"dispatched":false,"identity":null,"error":null}`.

3. Три независимых доказательства:

```bash
curl -s http://127.0.0.1:8788/healthz          # activeCalls остаётся 0
```
- в логе агента нет ни одной строки про этот `callId` (бэкенд ему вообще не писал);
- в списке участников комнаты нет identity `agent-relay` — видно в UI и в логах livekit-server.

Обратный тест: верните `lang` контакта на `he`, повторите — режим станет `TRANSLATED`, `activeCalls` станет 1, в комнате появится `agent-relay`.

Третья линия обороны — сам агент отказывается от DIRECT-джоба:

```bash
curl -s -X POST http://127.0.0.1:8788/jobs \
  -H 'content-type: application/json' \
  -H 'x-speakeasy-agent-key: dev-agent-secret' \
  -d '{"callId":"c_000000000000","roomName":"call-c_000000000000","mode":"DIRECT","livekitUrl":"ws://127.0.0.1:7880","token":"x","participants":[]}'
# -> 400 {"accepted": false, "reason": "direct_mode_no_agent"}
```

## 6. Как читать логи задержки

Агент пишет метрики **на каждый закоммиченный чанк**, по одному направлению за раз: строкой `speakeasy.latency {...}` в консоль и теми же полями в `latency` каждой `utterance`-записи eval-лога (§12). Имена полей одни и те же в обоих местах — это `UnitMetrics.stage_timings()` в `agent/src/speakeasy_agent/direction.py`.

| Поле | Что меряет | Ориентир `api` | Ориентир `mock` |
|---|---|---|---|
| `speech_start_to_first_partial_ms` | от начала речи до первого партиала STT | 150–350 | ~0 |
| `first_partial_to_commit_ms` | сколько чанкер держал префикс до коммита | 300–600 | ~400 |
| `commit_to_mt_done_ms` | коммит → готовый перевод, включая сеть | 250–400 | ~5 |
| `mt_provider_latency_ms` | из предыдущего — сколько занял сам провайдер | 250–400 | ~5 |
| `mt_done_to_first_audio_ms` | перевод → первый кадр в `AudioSource` (TTS TTFB + ресемплинг) | 130–210 | ~20 |
| **`speech_start_to_first_audio_ms`** | **воспринимаемая задержка целиком** | ≈ 0.95–1.8 с | 0.55–0.7 с |
| `tts_audio_ms` | длительность синтезированного аудио (не задержка) | — | — |

Как этим пользоваться:

- **Растёт итог, а стадии в норме** — смотрите `first_partial_to_commit_ms`: виноват чанкер, коммитит слишком поздно. Крутите `CHUNK_MIN_WORDS`, `CHUNK_MAX_SILENCE_MS`, `CHUNK_TIMEOUT_MS` в `.env`. Это самый частый источник «медленно», и он не про модели.
- **`mt_provider_latency_ms` > 600** — либо reasoning-токены включились (проверьте `thinkingLevel: "minimal"`), либо промпт распух историей (`MT_HISTORY_TURNS`).
- **`commit_to_mt_done_ms` заметно больше `mt_provider_latency_ms`** — время уходит в сеть, а не в модель.
- **`mt_done_to_first_audio_ms` под 800** — почти наверняка используется batch-режим синтеза вместо streaming.
- **Метрик нет вообще, а звонок идёт** — режим DIRECT (так и должно быть) либо агент не доехал до комнаты.

Перцентили по всем этим стадиям сразу считает review-CLI (§12) — руками их из лога выковыривать не надо.

Субъективный порог из [02-infrastructure.md](02-infrastructure.md) — 1.5–2.5 с. Всё, что укладывается в 1.8 с mouth-to-ear, на слух ощущается как «человек думает», а не как «система тормозит».

## 7. Тест вдвоём: что работает, а что физически нет

Здесь больше всего потерянного времени, поэтому по порядку.

### 7.1 Два браузера на одном Mac — работает всегда
Обе вкладки на `localhost`, secure context есть, микрофон разрешается, медиа не выходит из машины. Это режим для отладки механики. Ограничение: судить о задержке и естественности так нельзя — оба «человека» слышат один и тот же микрофон.

### 7.2 Телефон в той же Wi-Fi-сети — работает частично
Vite поднят с `--host`, `livekit.yaml` слушает `0.0.0.0`, страница откроется по `http://<ip-мака>:5173/?me=u_noa`. **Но микрофона на телефоне не будет.** iOS Safari отдаёт `getUserMedia` только в secure context, а `http://<lan-ip>` таковым не является (исключение сделано только для `localhost`). Самоподписанные сертификаты, по документации LiveKit, тоже не решают. Выглядит это как «LiveKit не работает», хотя LiveKit тут ни при чём.

Ваш IP:
```bash
ipconfig getifaddr en0
```

### 7.3 Тестер в другом городе или стране — LiveKit Cloud плюс туннель для страницы
Это тот самый случай, ради которого существует облачный профиль (§3.0) и [06-two-device-session.md](06-two-device-session.md). Одна фраза, которую надо понять правильно:

**Туннель не переносит WebRTC-медиа — и в облачном профиле ему это и не нужно.**

Разложим на две части, потому что раньше они были склеены в один запрет.

- **Туннель перед локальным SFU — по-прежнему запрещено.** Комната соединится, участники увидят друг друга, звука не будет ни в одну сторону. Причина структурная: SFU объявляет ICE-кандидатом свой собственный IP, а не hostname туннеля, и `rtc.node_ip` принимает IP, а не имя. Самый обманчивый отказ во всём стеке, потому что всё «зелёное». `npm run check:env` в облачном профиле падает на такой конфигурации явной ошибкой.
- **Туннель перед Vite при SFU в LiveKit Cloud — это рекомендованная схема.** Медиа идёт напрямую браузер → edge Cloud по UDP/ICE и туннеля не касается вовсе. Туннель нужен ровно для одной вещи: `getUserMedia` требует secure context, а `http://<lan-ip>:5173` им не является, поэтому без настоящего https-origin второй тестировщице **вообще не покажут запрос микрофона**.

Почему Cloudflare quick tunnel, а не альтернативы: не нужен аккаунт, нет промежуточной страницы-предупреждения, нет месячного лимита в 1 GB / 20k запросов. У ngrok всё это есть, зато есть закреплённое имя домена — единственное его преимущество здесь. Tailscale Funnel даёт стабильное имя и настоящий сертификат, но требует аккаунт и включённые MagicDNS/HTTPS; его сильная сторона — UDP-mesh до **локального** SFU — становится неактуальной ровно в тот момент, когда SFU переезжает в Cloud.

Единственная слабость quick tunnel: имя случайно и меняется при каждом старте. Поднимайте его один раз на сессию.

`web/vite.config.ts` уже разрешает `.trycloudflare.com`, `.ngrok-free.app`, `.ngrok-free.dev` и `.ts.net` в `allowedHosts`. Без этого Vite 8 отвечает голой страницей «Blocked request», в которой про туннели не сказано ничего. Ставить `allowedHosts: true` **нельзя** — это открывает исходники dev-сервера любому сайту в интернете.

### 7.4 TLS: всё или ничего
Страница по `https://` не откроет `ws://` — браузер молча блокирует mixed content. Если веб отдаётся по TLS, `LIVEKIT_URL` обязан быть `wss://`, и наоборот. Половинчатых конфигураций не бывает.

## 8. Переключение на реальных провайдеров

Правится только `.env`, затем перезапуск агента. Бэкенд и веб трогать не нужно (бэкенд читает имена провайдеров лишь для отображения в `/api/config`).

```bash

```

```dotenv
STT_PROVIDER=deepgram
MT_PROVIDER=gemini
TTS_PROVIDER=cartesia

DEEPGRAM_API_KEY=...
GEMINI_API_KEY=...
CARTESIA_API_KEY=...
CARTESIA_VOICE_RU=...     # обязательно: пустое ≠ «голос по умолчанию»
CARTESIA_VOICE_HE=...     # обязательно
```

```bash
npm run check:env        # ключи и голоса для выбранных провайдеров
```

Проверка теперь **падает с ошибкой**, если выбран `TTS_PROVIDER=cartesia`, а `CARTESIA_VOICE_HE` или `CARTESIA_VOICE_RU` пусты. Причина в [05-providers.md](05-providers.md), §11: пустое значение означает не «голос модели по умолчанию», а захардкоженный в плагине американский женский голос — для обоих языков и обоих людей.

Стадии независимы: `STT_PROVIDER=mock MT_PROVIDER=mock TTS_PROVIDER=cartesia` — валидная конфигурация и хороший способ послушать реальный ивритский синтез, не тратя ничего на STT и MT.

**Включать по одному, а не все сразу.** Стадии независимы по построению, и это единственный способ с первого раза понять, чей ключ не тот: `STT_PROVIDER=deepgram` → проверить → `MT_PROVIDER=gemini` → проверить → `TTS_PROVIDER=cartesia`. Порядок по возрастанию пользы на потраченный доллар другой: сначала TTS (слышимая разница мгновенная), потом STT, потом MT.

Матрица, цены и полный список исправлений в адаптерах — [05-providers.md](05-providers.md).

### 9.3 Лимиты бесплатного tier — исправление к более ранним разделам

Раньше в этом рунбуке и в [03-architecture.md](03-architecture.md) §1.5 стояло «5 одновременных соединений». **Это неверно, и построенный на этом риск «одна забытая вкладка убьёт тест» не существует.** Правильные цифры tier «Build»:

| Лимит | Значение | Что это для нас |
|---|---|---|
| Одновременных участников | **100** | двое людей + агент = 3. Забытые вкладки безвредны |
| Одновременных agent-сессий | 5 | это отдельный счётчик, его и путали с участниками |
| WebRTC participant-минут | 5 000/мес | ≈ **27,7 часа** переведённых звонков (3 участника = 3 минуты в минуту) |
| Трафик | 50 GB/мес | ≈ 26 000 минут: минуты кончатся раньше в ~15 раз |
| Agent session минут | 1 000/мес | ≈ 16 ч, если наш агент вообще считается по этому счётчику |
| STT / TTS соединений LiveKit Inference | 5 / 5 | нас не касается: мы ходим в Deepgram/Gemini/Cartesia напрямую |

Связывающий лимит для двух тестеров — participant-минуты, и до них далеко.

Открытый вопрос на минуту проверки в дашборде: `backend/src/livekit.ts` выпускает агенту токен с `agent: true` в `VideoGrant`, из-за чего участник помечается как `kind=AGENT`. Документация LiveKit по биллингу описывает счётчик agent-сессий как относящийся к агентам, *развёрнутым в LiveKit Cloud*, а наш агент self-hosted и заходит обычным участником по токену; что происходит в этом случае — не задокументировано. Даже в худшем варианте 1 000 минут ≈ 16 часов, так что это не блокер. Если на первом звонке в дашборде побегут agent-минуты и захочется их вернуть — удалить `agent: true` безопасно: клиент подписывается по имени трека (`tx-<userId>`), а не по типу участника.

## 10. Симптом → причина → лечение

| Симптом | Причина | Что делать |
|---|---|---|
| Комната соединяется, звука нет ни в одну сторону, ошибок нигде нет | Медиа идёт через туннель | Туннели не носят WebRTC. Перейти на LiveKit Cloud (§9) |
| Звука нет только у одного, у второго всё слышно | Агент опубликовал трек **после** `set_track_subscription_permissions` и не вызвал его заново | Права выдаются заново после каждой публикации; в track-level режиме новый трек не даёт прав никому. Логов об этом не будет |
| Звука нет, при этом в комнате видно `agent-relay` и обе дорожки | Клиент подписался не на ту публикацию | Подписка идёт по `trackName === "tx-<мой userId>"`, не по индексу и не по источнику |
| На iPhone нет микрофона, страница открывается | `http://<lan-ip>` — не secure context | Тестировать на самом Mac (`localhost`) либо через Cloud + TLS (§7.2, §7.3) |
| В консоли браузера заблокирован WebSocket | Страница по `https`, `LIVEKIT_URL` по `ws://` | Привести к одному: либо оба TLS, либо оба нет (§7.4) |
| Любой токен отвергается, `401`/`invalid token` | Ключ в `livekit.yaml` не совпадает с `.env`, либо забыт `await` у `toJwt()` | Блок `keys:` в конфиге подавляет автоподстановку devkey. `toJwt()` в SDK v2 асинхронный: без `await` токеном становится строка `"[object Promise]"` |
| В логе livekit-server ERROR про длину секрета | Секрет короче 32 символов | Не фатально, но исправить: `livekit-server generate-keys`, положить в оба места |
| `TRANSLATED`, но перевода нет и висит баннер «перевод недоступен» | Агент не поднялся или не дошёл `POST /jobs` | `curl http://127.0.0.1:8788/healthz`; проверить `AGENT_URL` и `AGENT_SHARED_SECRET` в `.env`. Молчаливого отката на сырое аудио собеседника нет — это осознанно |
| Агент отвечает `401` на джобы | Расходятся `AGENT_SHARED_SECRET` у бэкенда и агента | Обе стороны читают один и тот же `.env` — проверьте, что агент запущен из корня и видит его |
| Агент отвечает `409 already_running` | Для этого `callId` джоб уже есть | `curl -X POST http://127.0.0.1:8788/jobs/<callId>/stop` |
| `409 mode_locked` при смене режима | Звонок уже `active` | Смена режима на живом звонке в Этапе 0 не поддерживается. Завершить и создать заново |
| Перебивание не срабатывает: TTS доигрывает ещё секунду | `AudioSource` создан с дефолтным `queue_size_ms=1000` | Должно быть 200 — до секунды уже поставленного в очередь аудио иначе доиграет после отмены |
| Голос «бурундук» или замедленный | `rtc.AudioResampler.push()` возвращает **список** кадров, а обработан как один | Итерировать результат. Ошибки при этом не будет нигде |
| Пунктуация в ивритской строке уезжает в начало | Не выставлен `dir` по языку строки / нет `unicode-bidi: plaintext` | Это баг bidi-рендеринга, а не STT. См. [subtitles-ux.md](subtitles-ux.md) |
| Субтитры мерцают и переписываются | В основной поток попали партиалы | В окно коммитятся только финалы; партиалы живут в отдельном приглушённом слоте |
| Всё работало, после рестарта бэкенда контакты и звонки пропали | Хранилище в памяти | Так и задумано на Этапе 0. Настройки контактов задавать заново через `PATCH /api/users/:id/contacts/:peer` |
| `Cloud`: не пускает в комнату | **Не лимит соединений** — их 100, а не 5 (§9.3) | Смотреть на токен и на `LIVEKIT_API_KEY`/`SECRET`: в облаке `devkey` не работает, `check-env` в профиле `cloud` ловит это ошибкой |
| Страница отдаёт голое «Blocked request» | Vite 8 не знает этот Host | Домен туннеля должен быть в `allowedHosts` в `web/vite.config.ts`. Никогда не `true` |
| У удалённого тестера нет запроса микрофона | Страница не в secure context: `http://<lan-ip>` | Только `https://` или `localhost`. Клиент диагностирует это отдельным сообщением (`web/src/secure.ts`) |
| Страница по https, каждый запрос API падает | `VITE_BACKEND_URL` остался `http://127.0.0.1:8787` | `VITE_BACKEND_URL=/` **и перезапустить web**: Vite читает `.env` один раз при старте, на живом процессе значение не подхватится и ошибки не будет |
| Ссылку скопировали, а она с `localhost` | Основатель открыл свою страницу по localhost | Приглашение строится из `window.location`. Открывать адрес туннеля на обеих машинах |
| Тестировщица открыла страницу, но в контактах серая | Не идёт heartbeat | `curl -s http://127.0.0.1:8787/api/ring/u_noa`. Проверить, что `PRESENCE_TTL_SECONDS` ≥ 15 с — это 3× самого медленного реального опроса, `RING_POLL_HIDDEN_MS`=5000 мс в `web/src/ring.ts` (а не 3× `VITE_POLL_INTERVAL_MS`, которое не читает никто) |
| Звонок не приходит вообще, ссылка-приглашение работает | Клиент выключил опрос, не найдя ринг-маршрутов | Так задумано: без них он молча откатывается к ссылке. Проверить `/api/config` — там должен быть блок `ring` |
| `Accept` отвечает `409 ring_conflict` | Звонок уже не звонит: истёк (45 с), отменён или отклонён | Позвонить заново |
| `POST /api/calls` отвечает `409 busy` | У кого-то из двоих уже есть звонящий звонок | Отменить или ответить на него; истёкшие подметает сам бэкенд |
| Вердикт: `409 no_agent` | Звонок `DIRECT` — переводить было нечего | Не ошибка |
| Вердикт: `404 not_found` (агент отвечает `unknown_call`) | У агента нет файла лога для этого `callId` | Этот агент никогда не обслуживал этот звонок |
| Вердикт: `502 agent_unreachable` | Бэкенд заворачивает в 502 **любой** не-2xx и не-404 ответ агента — включая `409 eval_log_disabled` при `EVAL_LOG_ENABLED=false` | Читать текст ошибки до конца: там дословный ответ агента. Слово «unreachable» здесь может врать |
| Вердикт принят, но `resolved: false` | Не удалось привязать к реплике | Строка в файле есть; отчёт покажет её как orphan. Сознательный выбор: терять метку судьи хуже, чем держать сироту |
| Иврит в TTS звучит с ошибками ударения/омографов | Отсутствие огласовок (никуд) | Это ожидаемое поведение, не баг интеграции. Точечное лечение — никуд прямо в тексте для конкретных слов, см. [05-providers.md](05-providers.md) |

## 12. Eval-лог и разбор звонка

### 12.1 Что пишется

На каждый **переведённый** звонок агент заводит `logs/calls/<callId>.jsonl` — по строке JSON на событие, дописывается по ходу, так что падение посреди сессии оставляет всё до этого момента читаемым. Файл создаётся в момент старта реле, поэтому «файла нет» честно означает «этот агент такого звонка не обслуживал».

| `kind` | Когда | Что несёт |
|---|---|---|
| `call` | один раз при старте реле | `mode`, `roomName`, тройка провайдеров, оба участника |
| `utterance` | на каждую закоммиченную единицу | `utteranceId`, `direction`, `srcText`, `dstText`, пол говорящего и слушающего, `tone`, `trigger`, `latency{...}`, `providers`, `cancelled`, `error` |
| `verdict` | на каждый вердикт судьи | `utteranceId`, `verdict` (`wrong`/`ok`), `expected`, `note`, `by`, `resolved` |

Вердикты **дописываются, а не вклеиваются** в строку реплики: файл append-only, поэтому второй вердикт на ту же реплику виден как смена мнения, а не молча затирает первый.

Запись никогда не блокирует и никогда не роняет аудио-путь: `append()` кладёт запись в ограниченную очередь, фоновая задача пишет на диск в отдельном потоке, переполнение очереди — предупреждение и потеря записи, любая ошибка файловой системы логируется и глотается. Сломанный eval-лог портит эксперимент, но не звонок.

Всё это работает **и на mock-провайдерах** — весь путь от кнопки до строки в файле проверяется офлайн, без единого ключа.

Выключается `EVAL_LOG_ENABLED=false`; `check-env.mjs` при этом предупреждает, что вердикту станет не к чему прикрепляться.

### 12.2 Чем читать

```bash
cd /Users/davidov/SpeakEasy/agent
uv run python scripts/review_call.py --list
uv run python scripts/review_call.py c_ab12cd34ef56
uv run python scripts/review_call.py c_ab12cd34ef56 --flagged
uv run python scripts/review_call.py c_ab12cd34ef56 --json
uv run python scripts/review_call.py --dir /path/to/archive c_ab12cd34ef56
```

Отчёт печатает шапку (режим, провайдеры, участники), все реплики с исходником и переводом, помеченные — с исправлением судьи, затем перцентили по всем стадиям из §6 и по сквозной задержке, затем счётчики: закоммичено, доставлено, отменено при перебивании, ошибки провайдеров, вердикты, доля флагов и покрытие судейством, с разбивкой по направлениям. Если провайдеры были моковыми — говорит об этом прямым текстом.

Флаг `--isolate` оборачивает RTL-текст в Unicode-изоляты U+2067/U+2069. По умолчанию выключен: часть терминалов их реализует и рендер улучшается, часть рисует вместо них квадратики. Инструмент принципиально ничего не переупорядочивает сам и помечает язык каждой строки, потому что корректный bidi в терминале извне не чинится.

### 12.3 Две обёртки разбора — чем отличаются

Обе читают один и тот же JSONL и обе работают (проверено на файле, сгенерированном самим `evallog.utterance_record()`).

| Инструмент | Что даёт | Когда брать |
|---|---|---|
| `agent/scripts/review_call.py <callId>` | построчный разбор: каждая реплика с оригиналом и переводом рядом, помеченные выделены с ожидаемым текстом, перцентили по этапам | разбор вдвоём с тестировщицей сразу после звонка |
| `npm run review <callId>` | сводка: сколько реплик, сколько помечено неверными, **доля принятых переводов**, перцентили, список помеченных | быстрая оценка «стало лучше или хуже» между прогонами |

Ключевое поле сводки — доля принятых переводов среди тех, что судили. Именно её сравнивают между двумя прогонами при смене модели; абсолютные цифры задержки при этом смотрят отдельно, потому что качество и скорость меняются независимо.

Записи о провайдерах содержат конкретную модель и голоса, а не только семейство (`cartesia:sonic-3.5-2026-05-04/he=…,ru=…`), поэтому два A/B-прогона в логе различимы.

## 13. Диагностика звонка-вызова

Звонок и presence сделаны **опросом, без websocket'ов на бэкенде** — сознательно: двое тестеров при паре запросов в секунду не создают нагрузки, а опрос не умеет наполовину отвалиться, как оборванный сокет.

Один запрос `POST /api/presence` возвращает сразу всё: себя, контактов, входящий звонок и статус исходящего. Тот, кто обязан отмечаться живым, — ровно тот, кто обязан узнать о входящем.

Посмотреть глазами любой из сторон, ничего при этом не меняя:

```bash
curl -s http://127.0.0.1:8787/api/ring/u_noa | python3 -m json.tool
curl -s http://127.0.0.1:8787/api/ring/u_alex | python3 -m json.tool
```

Прогнать весь цикл руками, без браузера:

```bash
curl -s -X POST http://127.0.0.1:8787/api/calls \
  -H 'content-type: application/json' \
  -d '{"callerId":"u_alex","calleeId":"u_noa","ring":true}'

curl -s -X POST http://127.0.0.1:8787/api/calls/<callId>/ring/accept \
  -H 'content-type: application/json' -d '{"userId":"u_noa"}'
```

Тайминги и где они живут:

| Что | Значение | Переменная / файл |
|---|---|---|
| Опрос, пока что-то звонит | 1200 мс | `web/src/ring.ts` |
| Опрос в покое | 2500 мс | там же |
| Опрос в фоновой вкладке | 5000 мс | там же |
| Пол потолка бэкоффа при ошибках | 750 мс … 30 с | там же |
| Онлайн после последнего опроса | 15 с | `PRESENCE_TTL_SECONDS` |
| Неотвеченный звонок звонит | 45 с | `RING_TIMEOUT_SECONDS` |
| Завершённый ринг ещё виден звонящему | 20 с | `RING_RESULT_GRACE_MS` в `backend/src/ringing.ts` |

Три вещи, которые стоит знать заранее:

- **Отказ, отмена и таймаут — один и тот же код**, отличается только надпись. Все три завершают звонок **и останавливают агента**. Агент, забытый в комнате после отклонённого звонка, — тихая утечка и минут LiveKit, и вендорских минут STT.
- **Истечение проверяется дважды**: лениво, в начале каждого обработчика, чтобы опрос физически не мог увидеть ринг, который должен был уже умереть; и фоновым интервалом раз в секунду, чтобы брошенный звонок отпустил агента, даже когда оба браузера ушли и никто не опрашивает.
- **Двойной `accept` — успех, а не ошибка.** Повторное нажатие или ретрай после мигнувшей сети возвращает `alreadyAccepted: true`, а не «звонка, в котором вы уже находитесь, не существует».

Если `PRESENCE_TTL_SECONDS` меньше трёх самых медленных интервалов опроса (3 × 5000 мс = 15 с), `check-env.mjs` предупредит: вкладка, ушедшая в фон, мигнёт офлайн посреди звонка. Сравнение идёт именно с `RING_POLL_HIDDEN_MS` из `web/src/ring.ts`, а не с `VITE_POLL_INTERVAL_MS`: последнее ни один файл не читает, и раньше проверка пропускала конфигурации, которые ломались в фоне.
