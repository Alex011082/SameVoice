## 1. Что это

Мессенджер и коммуникационная сеть, в которой **язык человека больше не имеет значения**. Язык — свойство контакта, задаётся один раз; дальше перевод исчезает из интерфейса как действие. Нажал 📞 — говоришь на своём языке, собеседник слышит свой, в идеале — твоим голосом.

**Принципы:**
- *You don't choose a language. You choose a person.*
- *AI is not in the call path unless it is needed* — при совпадении языков полный bypass ИИ, чистый WebRTC.

**Тезис:** «Мы строим коммуникационную сеть, в которой язык человека больше не имеет значения» — не «WhatsApp с переводчиком».

Полная выжимка исходной концепции (тарифы, Random Voice, PSTN, связка с YTNG) — [00-concept.md](00-concept.md). Независимая оценка идеи, риски, план запуска — [01-assessment-claude.md](01-assessment-claude.md).

## 2. Место в экосистеме и имя (решено 24.08.2026)

Продукт — **пятый в экосистеме 0110.digital**, наряду с Jarvis (операционная система экосистемы), ЛидМашиной (поиск клиентов для малого бизнеса), YTNG (перевод бизнеса на другие языки) и продуктом «0110» — B2B-вертикалью для владельцев dev/digital-бизнесов (см. `~/Jarvis/docs/ECOSYSTEM.md`).

**Домены:** единая точка входа `0110.digital`, продукты на поддоменах: `dev.0110.digital`, `bob.0110.digital`, `lead.0110.digital`, `ytng.0110.digital`, **`samevoice.0110.digital`** — наш.

**Открытый вопрос вне этого проекта:** имя вертикали «0110» из ECOSYSTEM.md конфликтует с именем зонтичного бренда 0110.digital — два разных смысла у одного слова. Переименование вертикали — задача Jarvis-проекта, не наша.

**Имя продукта:** рабочее — **SameVoice (0110)**. История проверки:
- «Speak Easy» — **отклонено**: в сторах уже живут одноимённые переводчики, действующий трейдмарк класса 9.
- «Small Talk» — **отклонено**: занятая регистрация с 1999-го, язык программирования Smalltalk, ненаходимо в принципе.
- «No Border Talk» — рискованно: есть японский конкурент «Borderless Talk» с почти тем же именем.
- «SameVoice» голым словом — **рискованно**: словосочетание почти буквально описывает саму технологию голосового клонирования при переводе (подтверждено названием научной статьи ACM IUI 2026 «Same Voice, Different Language») — бьёт по различительности и находимости, как SpeakEasy/SmallTalk. `samevoice.com` не конкурент — это домен-брокер (namestar.com) за Cloudflare-защитой, ложная тревога.
- **«SameVoice (0110)»** как составной знак — жизнеспособно: приставка 0110 превращает родовую фразу в узнаваемый бренд и привязывает к уже существующему домену. TESS/EUIPO напрямую не проверялись (доступ агента заблокирован) — перед реальной подачей нужен патентный поверенный.

Полный разбор проверки имён и попутно — каталога Public Endpoints RunPod — [eval/naming-and-runpod-endpoints.md](../eval/naming-and-runpod-endpoints.md).

## 3. Режим работы над проектом

Разработка — основатель с Claude Code, соло. Тестеров двое: основатель (RU, male) и ивритоговорящая женщина, сама носитель русского (RU, female) — она **билингвальный судья**: слышит и оригинал, и перевод, может сразу сказать, верен ли он. Это ценнее нативного ивритоговорящего тестера, который не может оценить русский выход.

Три оговорки к её вердиктам: её иврит с русским акцентом делает распознавание пессимистичнее общего случая; оба тестера русскоязычные — риск, что разговор получится «переводческим», слишком простым; mock-режим ничего не говорит о качестве перевода.

Аппаратное ограничение разработки: рабочая машина — **Apple M1, 8 GB RAM**. Тяжёлые модели локально не живут; Mac держит только media+control (LiveKit SFU, бэкенд, веб, тонкий агент), AI-стадии — за провайдер-абстракцией.

## 4. Текущее состояние: скелет Этапа 0

Полностью рабочий стек. `git init` выполнен 24.08.2026, первый коммит — 121 файл, без секретов (найден и удалён `.env.local-sfu` с реальным `LIVEKIT_API_SECRET`, `.gitignore` дополнен паттерном `.env.*` с исключением `.env.example`).

**Состав:**
- **backend** — Node 26 + TypeScript + Fastify 5, минтинг токенов LiveKit, решение режима звонка (DIRECT/TRANSLATED/FORCED), presence и вызов (ringing), вердикты судьи.
- **agent** — Python 3.13 (uv) + livekit-agents 1.7.0, реле перевода на низкоуровневых rtc-примитивах, полный пайплайн одного направления, eval-лог.
- **web** — Vite + TypeScript без фреймворка, контакты, экран звонка, живые субтитры (RTL по языку строки, уже показанный текст не переписывается), кнопка «Wrong translation».
- **livekit-server** локально по умолчанию, LiveKit Cloud — сменой трёх переменных `.env`.

**Тесты:** 236 проходят (50 backend node:test + 105 agent pytest + 81 web vitest). Ноль ключей, ноль Docker, ноль GPU для базового прогона — тесты идут на mock-провайдерах независимо от того, что стоит в `.env`.

**Измеренная задержка (mock-провайдеры, локально):** 1.26–1.56 с сквозная (speech→first audio), с отменой синтеза при перебивании (barge-in) — работает.

**Главный принцип проверен машинно:** в DIRECT `GET /healthz` агента → `activeCalls: 0` — ИИ действительно вне тракта при совпадении языков.

Полная архитектура с обоснованием каждого решения (одна комната + выборочная подписка, свой процесс агента вместо `AgentSession`, провайдеры, языки/тулчейн) — [03-architecture.md](03-architecture.md). Эксплуатация, порты, отказы — [04-runbook.md](04-runbook.md). Гид по сессии вдвоём — [06-two-device-session.md](06-two-device-session.md).

## 5. Архитектурные решения (сухой остаток)

- **Одна LiveKit-комната** на звонок, не мост из двух — экономии по задержке нет, а DIRECT без общей комнаты невозможен в принципе.
- **Изоляция слушателя** — три слоя: клиент подписывается выборочно (`autoSubscribe:false`), агент принудительно ограничивает permissions после публикации обеих дорожек, (не в Этапе 0) сервер дублирует контроль.
- **Агент — самостоятельный процесс**, не `AgentServer`-воркер с автодиспетчеризацией: последняя заходит в каждую комнату, что нарушает принцип bypass на уровне архитектуры, а не настройки.
- **Низкоуровневые rtc-примитивы**, не приватные API `voice._*` — платим чуть менее точной синхронизацией субтитров, получаем стабильность между патчами.

## 7. ElevenLabs v3 — разбор и вывод

Повод: основатель сгенерировал качественный ивритский клип клонированным голосом (PVC) через ElevenLabs v3. Проверка показала: **иврит у ElevenLabs есть**, но только в семействе v3 — прежнее утверждение «иврита нет вообще» было неполным для v3, хоть и верным для Multilingual v2/Flash v2.5/Turbo v2.5.

**Для живого звонка v3 не годится**, по четырём независимым причинам: вендор сам пишет «not suitable for real-time»; `eleven_v3_conversational` даёт ~280 мс инференса сверх сети; фиксированный порог ~40 символов/8 слов до первого чанка — короткие реплики звонка (`רגע.`) не запускают генерацию вовсе; PVC-голоса — самый медленный класс, официально не оптимизирован под v3 и обучается только на моделях без иврита.

**Вывод:** Cartesia остаётся для звонка. **ElevenLabs v3 — кандидат №1 для асинхронных голосовых сообщений**, где задержка не важна, а качество важно — это открыло новую продуктовую линию, которую прежнее исследование закрывало по ошибке. Полный разбор, включая арифметику My Voice при +$1.99/мес и требования EU AI Act к согласию/водяным знакам — [eval/elevenlabs-v3-findings.md](../eval/elevenlabs-v3-findings.md).

## 8. Открытый ивритский TTS — VoxCPM2

**Заявление, которое было неверным:** «ивритский TTS нельзя self-host'ить вообще» — этим обосновывался отказ от аренды GPU. Найден **VoxCPM2** (OpenBMB, k2-fsa): 2B параметров, иврит в списке 30 языков, **веса Apache-2.0**, 48 кГц, zero-shot клонирование, настоящий стриминг. Опубликованный ориентир авторов — RTF 0.3 на RTX 4090.

**Дисквалифицированная альтернатива:** движок по умолчанию в каталоге VoiceStudio, **k2-fsa/OmniVoice**, оказался непригоден трижды независимо — веса **CC-BY-NC** (не Apache, как ошибочно указано в README VoiceStudio), иврит объективно слабый (CER 9.75 против 4.91 у человека, 4-й худший результат из 102 языков в их же статье), архитектура — неавторегрессионная диффузия, стриминг физически невозможен.

### 8.1 Живой тест на RunPod (24.08.2026)

Под: RTX 4090, 24 GB, регион EU-RO-1, $0.74/час, On-Demand. Подключение — через проксисервис `ssh.runpod.io` (прямой TCP-порт ключ не принимает: RunPod вшивает публичный ключ в контейнер только при старте, добавление ключа в аккаунт задним числом не действует на уже запущенный под). Передача файлов — только через PTY-сессию (SCP/SFTP-каналы прокси не поддерживает, требует PTY даже для exec), проверено base64 + сверка SHA-256 на обоих концах на каждом файле.

**Замеры без клонирования (стоковый голос модели), 5 фраз из тестового набора:** RTF стабильно **0.367–0.376** — лучше опубликованного ориентира 0.3 для 4090 (в пределах шума измерения). Модель быстрее реального времени в 2.7 раза.

**Оценка основателя (не носитель иврита, судит естественность звучания), стоковый голос:** greeting/homograph/short1/short2 — хорошо; **gender_f** («את שומעת אותי טוב?») — плохо, забраковано.

**Замеры с клонированием голоса Ellen** (референс — 12-секундный клип из ElevenLabs, 16 кГц моно, переданный с проверкой SHA-256 на обоих концах): RTF **0.373–0.431**, клонирование почти не замедлило генерацию. Оценка основателя, клонированный голос: **greeting/gender_f/homograph/short1 — хорошо** (gender_f, ранее забракованный на стоковом голосе, с клонированным голосом звучит нормально — похоже на свойство именно стокового тембра, не текста или грамматики); **short2** («בסדר, אין בעיה.») — плохо, забраковано.

**Диагностика short2 (тот же сеанс):** 5 повторных генераций той же фразы тем же клонированным голосом плюс два новых коротких предложения («לא, לא זה.», «מה? לא הבנתי.»). Длительность вышла разной при одинаковом тексте (1.12–1.28 с) — **модель стохастична**, это подтверждает, а не опровергает гипотезу случайного сбоя, а не системного дефекта конкретно на этой фразе. Встроенный `retry_badcase` (включён по умолчанию в API) ловит только выбросы по соотношению длина-аудио/длина-текста; «звучит плохо, но длина в норме» он не поймает. Короткие реплики — предсказанная в [eval/hebrew-tts-test.md](../eval/hebrew-tts-test.md) п.10 зона риска для любого TTS, и для живого звонка это больше половины реплик — вопрос принципиальный, ждёт вердикта тестировщицы по всем повторам.

**Вердикт диагностики (основатель):** из пяти повторов `short2_repeat3` — лучший результат; остальные не забракованы. Обе новые фразы, `clone_short3` и `clone_short4`, оценены как «очень хорошо». **Вывод: изначальная плохая генерация short2 — outlier конкретного прогона, не устойчивый дефект фразы или модели на коротких репликах.** Риск, отмеченный в hebrew-tts-test.md п.10, существенно снижен этим тестом, но не снят до конца: разброс между генерациями означает, что продукту в проде понадобится либо оценка качества результата перед воспроизведением (например, по той же audio/text-ratio эвристике, что уже есть в `retry_badcase`, но с более чувствительным порогом), либо принятие того, что изредка одна фраза в звонке будет звучать похуже — вопрос дальнейшей инженерии, не блокер для дальнейших тестов.

**Правило, применяемое ко всем самостоятельным оценкам в этом проекте:** основатель (не носитель иврита) может судить, звучит ли естественно. Правильность — грамматический род, омографы без огласовок (сефер/сафар, халав/хелев), согласование числительных — может судить только говорящий на иврите, и только **вслепую**, без текста перед глазами.

**Не решено этим тестом:** GPU-latency-гейт (время до первого чанка в потоковом режиме, streaming API модели не тестировался — только `generate()` целиком) и вердикт билингвальной тестировщицы по правильности иврита на всех прогонах.

Полный разбор лицензий, конкурентов по каталогу (VoxCPM2/MOSS-TTS/dots.tts и др.), плана адаптера `tts_voxcpm.py` — [eval/open-hebrew-tts-findings.md](../eval/open-hebrew-tts-findings.md).

### 8.2 Что это меняет, если подтвердится

- **My Voice** — экономика переворачивается: себестоимость N-го клонированного голоса → 0, вместо потолка в 660 голосов и посимвольной оплаты у ElevenLabs.
- **Аренда GPU** становится осмысленной для call-пути, а не только для async — но только после прохождения gate качества (сделан сегодня) и gate задержки (стриминг на живом ключе, следующий шаг).
- **Vendor lock на Cartesia снимается** как единственно возможный вариант — появляется self-hosted путь.

## 9. Инфраструктура и география

**Ошибка, найденная и исправленная 24.08.2026:** документы утверждали, что у LiveKit нет edge в Израиле и медиа идёт в Европу (~85–103 мс), с рекомендацией переселить агента в регион `eu-central` ради экономии ~180 мс. **Проверено самостоятельно:** `speak-easy-xul1tkud.livekit.cloud` резолвится в Oracle Cloud, **Иерусалим** — TCP connect **20 мс** медиана. Рекомендация переселить агента в Европу **добавила бы** ~120 мс, а не убрала. Оба документа ([04-runbook.md](04-runbook.md) §9.4, [02-infrastructure.md](02-infrastructure.md) §8) исправлены.

**Решение по серверу — выполнено 24.08.2026.** SFU остался на LiveKit Cloud (свой self-hosted SFU дал бы только ~7 мс выигрыша ценой TURN-over-TLS, сертификата и мониторинга — плохая сделка при двух тестерах). Бэкенд, агент и веб перенесены на **израильский VPS**: **Vultr, Tel Aviv, 1 vCPU / 2 GB, $10/мес**, сервер `samevoice` @ `64.176.170.106`, Ubuntu 26.04 LTS.

Развёрнуто и проверено:
- Firewall (ufw): только 22/80/443, автообновления безопасности включены.
- **Caddy** — автоматический TLS через Let's Encrypt (боевой `acme-v02`, не staging), обслуживает `https://samevoice.0110.digital`, статика веба + reverse proxy `/api/*` и `/healthz` на бэкенд.
- **Node 26 + uv/Python 3.13**, backend собран в production-режиме (`tsc` → `dist/`, не `tsx watch`), веб собран статикой (`vite build`).
- Оба процесса — **systemd**-юниты (`samevoice-backend`, `samevoice-agent`) с `Restart=always`, отдельный непривилегированный пользователь `speakeasy`, не root.
- DNS: A-запись `samevoice.0110.digital → 64.176.170.106` в GoDaddy (там же держится весь `0110.digital`, NS-записи и остальные записи домена **не трогать** — общая инфраструктура экосистемы, не только SpeakEasy).
- LiveKit Cloud — тот же проект, что тестировался раньше (`wss://speak-easy-xul1tkud.livekit.cloud`), ключи перенесены на сервер.
- Провайдеры на сервере — **реальные, включены 24.08.2026**: `STT_PROVIDER=deepgram`, `MT_PROVIDER=gemini`, `TTS_PROVIDER=cartesia`. Подтверждено на `/healthz` агента. Тест качества перевода живым голосом ещё не проводился — это следующий шаг.
- **Голоса именуются метками, реестр — [eval/voices.md](../eval/voices.md).** «Голос L», «голос Alex» — это записи оттуда; идентификаторы вида `f247a379-…` сами по себе ничего не значат. ## 10. Методика тестирования

**Eval-лог:** каждая переведённая реплика пишется в `logs/calls/<callId>.jsonl` — оригинал, перевод, пол обоих участников, тон, все замеры задержки по стадиям, конкретные модель+голос провайдеров (не только семейство — иначе A/B-прогоны неразличимы в логе).

**Кнопка судьи:** во время звонка одним нажатием помечает последнюю реплику неверной, с полем «должно было быть так» — превращает тестировщицу в источник размеченных данных, а не мнений.

**Разбор сессии:** `npm run review <callId>` — сводка с долей принятых переводов (метрика для сравнения A/B), `agent/scripts/review_call.py <callId>` — построчный разбор оригинал/перевод рядом.

**Тестовый набор для TTS/произношения:** 10 категорий (базовая фраза, род говорящего/слушателя, омографы без огласовок, числа, code-switching с английским, аббревиатуры, длинная фраза с паузами, эмоция, короткие реплики) — [eval/hebrew-tts-test.md](../eval/hebrew-tts-test.md).

**Правила живых субтитров:** стабилизация частичных гипотез (LocalAgreement-2, не переписывать показанное), перевод крупно/оригинал мельче, `dir` поэлементно по языку строки — [subtitles-ux.md](subtitles-ux.md).

### Первый живой звонок на реальных провайдерах (24.08.2026, ~17:45–17:55)

Основатель и тестировщица, `samevoice.0110.digital`, TRANSLATED. Звонок **провалился**, но диагностически он был очень полезен. Логи — `c_ba1942745865.jsonl` (36 реплик за 1.6 мин) и соседние.

**Причина №1 — рейт-лимит Gemini, доказан.** 13 реплик из 36 умерли с `HTTP 429: generate_content_free_tier_requests, limit: 15`. Реальная нагрузка — **22.8 запроса в минуту** (обе стороны вместе), то есть бесплатный тариф пробивается сразу. Симптом «слышала первые пару секунд, потом тишина» — это ровно момент исчерпания лимита. Лечение — предоплаченный биллинг Gemini; после его включения ошибка сменилась на `prepayment credits are depleted`, то есть **на момент записи оплата так и не внесена, тест не повторён**.

**Причина №2 — мусор в распознавании иврита, НЕ решена.** Её реплики местами расшифровывались бессмыслицей (`פוגע בדמות אונס`, `את הנל הפסטריאטות של סנפיס אין ברימה`), которую Gemini честно переводил как бессмыслицу. **Deepgram при этом не виноват:** на чистом синтезированном иврите тот же ключ и модель дают confidence **0.983** и почти дословную расшифровку. Значит причина — микрофон, потери пакетов или русский акцент, и **разделить эти версии по текущему логу невозможно**.

**Дыра в логировании, найденная этим звонком:** confidence от STT нигде не пишется. Сейчас в eval-логе неотличимо «распознаватель сомневался» от «уверенно выдал не то» — а это разные диагнозы с разным лечением. Поле стоит добавить в `providers/stt_deepgram.py` и в схему eval-лога.

**Транспорт основателя был нестабилен:** ~10 событий `participant left mid-call: u_alex`. Отсюда же выбросы задержки `speech_start_to_first_audio_ms` в 15–16 с при нормальных 3.1 с на той же сессии — тормозили не провайдеры, а доставка звука.

**Что при этом работало верно.** Реплики, прошедшие до лимита, переведены корректно, включая род: «Слышно меня?» → `שומעים אותי?`. Женский голос, который основатель услышал и принял за глюк, оказался правильной работой системы — тестировщица спросила `שפה אתה רוצה לדבר?`, перевод «на каком языке ты хочешь говорить» прозвучал голосом Ellen.

**Замеренная задержка на реальных провайдерах** (лучшая реплика сессии): STT 1675 мс → коммит 456 мс → MT 683 мс → первый звук 290 мс, **итого 3.1 с**. Это вдвое выше целевого коридора 1.5–2.5 с, и основной вклад даёт STT, а не перевод.

### Второй провал: звонок в мёртвую комнату (25.08.2026)

Тест двух человек снова не состоялся — но на этот раз **тракт был исправен**, а виновата оказалась память бэкенда. Звонок `c_f74783a70042` создан 24.08 в 17:48 и в 08:38 следующего утра всё ещё числился живым: in-memory стор ничего не завершает по таймауту и ничего не удаляет, поэтому звонок в нём бессмертен. Клиент раз за разом слал `POST /api/calls/c_f74783a70042/join`, получал 409 и не отступался, пока вторая сторона создавала свежие звонки. В одну комнату LiveKit они так и не попали и не услышали друг друга — при том что агент отработал безупречно (`committed=5 spoken=4 errors=0`), а сам агент ещё и продолжал показывать `activeCalls: 1` по мёртвому звонку, пока его не перезапустили руками.

Инцидент снят перезапуском `samevoice-backend` (стор в памяти), причина закрыта тремя границами:

- **Время жизни звонка, бэкенд** (`backend/src/store.ts` + `ringing.ts`). Звонок, в который никто не вошёл и который не держит живой ring, завершается через **10 минут** простоя; звонок, в который вошли, — через **3 часа** от создания. Второй потолок именно потолок, а не политика длительности: браузер не сообщает бэкенду ни «я ещё здесь», ни «я закрыл вкладку» (на `pagehide` он гасит медиа, но не шлёт `/end`), так что более точного сигнала у сервера просто нет. Живой звонок из памяти не выселяется никогда. Счётчики видны снаружи: `GET /healthz` → `calls: {live, ended}`.
- **Архив вместо удаления** (`backend/src/archive.ts`). Завершённый звонок завершён сразу, но он не мусор: это запись разговора двух людей, и расшифровки с воспроизведением будут строиться поверх неё. Ещё 10 минут запись доступна по обычному `GET /api/calls/:callId` (чтобы клиенту, который опоздал, было чем объяснить, почему звонок кончился), после чего уходит из памяти в архив — один JSON-файл на звонок в `CALL_ARCHIVE_DIR` (`logs/archive`, gitignored). Читают её только те двое, кто на этом звонке был: `GET /api/users/:userId/calls[/:callId]`; чужой звонок отдаёт `404`, а не `403`, потому что 403 сам по себе подтвердил бы факт звонка. На диске, а не во второй Map, ровно по причине этого же инцидента — бэкенд перезапускают часто, и архив, который чистится `systemctl restart`, не архив. Вторая половина записи — eval-лог агента `logs/calls/<callId>.jsonl`, сходится по тому же `callId`. **Пока это только запись и хранение:** ни расшифровок, ни UI поверх архива ещё нет.
- **Пустая комната, агент** (`agent/src/speakeasy_agent/relay.py`). Комната без людей 120 секунд — реле само отключается и освобождает участника LiveKit и две открытые STT-сессии. LiveKit сам этого не сделает: его `empty_timeout` считает участников, а агент — участник. Порог с запасом больше всего окна ринга (45 с на ответ + 45 с на «приняли, но не вошли»), потому что агент диспатчится в момент СОЗДАНИЯ звонка и пустая комната в это время — норма.
- **Автоподключение, клиент** (`web/src/autojoin.ts`). 409/404 на join — id мёртв для этой вкладки навсегда, повторов больше нет. Ring, который эта вкладка не начинала и у которого дедлайн уже прошёл, не подхватывается вовсе — именно так вчерашний звонок попадал в сегодняшнюю сессию. Живой ring подхватывается по-прежнему: это звонящий, у которого страница перезагрузилась во время вызова, и он должен соединиться.

**Что из этого следует для методики:** «пайплайн работает» и «звонок состоялся» — разные утверждения, и eval-лог подтверждает только первое. Тест двух человек считается проведённым, лишь когда обе стороны оказались в одной комнате; проверяется это одним `curl` на `/healthz` бэкенда и агента до начала разговора.

### Замер своего стека на GPU (26.08.2026) — что выяснено за $7

Арендован RTX 4090 после того, как облачный путь упёрся в **4045 мс** и стало
ясно, что ни один вендор не даёт одновременно быстрый иврит и свой голос.
Обвязка и разбор кандидатов — [eval/selfhosted/](../eval/selfhosted/) и
[eval/self-hosted-stack.md](../eval/self-hosted-stack.md).

**Синтез — НЕ узкое место, и это теперь доказано числами.** VoxCPM2 на карте
отдаёт первый звук за **54–64 мс** без клона и ~100 мс с клоном, против 260 мс
у Cartesia в бою. Но синтез занимал 260 мс из 4045 — то есть даже полная победа
здесь экономит четверть секунды. **Три секунды из четырёх лежат в распознавании
и ожидании конца фразы, и мерить надо было сразу их.**

**VoxCPM2 в потоковом режиме непригоден.** В логе строка
`Retry on bad cases is not supported in streaming mode, setting retry_badcase=False`:
стриминг **отключает встроенный сторож качества**. Отсюда «мычание коровы» в
вердикте основателя — при том, что 24.08 он же одобрил ту модель в пакетном
режиме, где сторож работает. Вывод: VoxCPM2 может быть быстрым **или** хорошим.

**Кросс-языковое клонирование не работает в открытых моделях.** Русский
референс + ивритский синтез = сломанный голос (проверено на VoxCPM2 и Palabra).
Клонирование работает **внутри** языка: тот же VoxCPM2 на ивритском референсе
звучал приемлемо. **Cartesia остаётся единственным вендором, у кого перенос
русского голоса на иврит получается** — клон основателя снят с русской записи и
одобрен им же.

**Решение основателя, превращающее это ограничение в продукт:** просить
пользователя записать транскрипцию на целевом языке — «хочешь звучать собой на
иврите, прочитай этот текст и пришли запись» — и продавать это как платную
фичу. Технически это переводит задачу из кросс-языковой (не работает нигде) в
внутриязыковую (работает везде). **Акцент в клоне признан фичей, а не багом:**
так человек и звучал бы, выучив язык; это честнее, чем его тембр с
произношением диктора.

**Дорогой урок про GPU.** $7 ушли в основном на `pip install` при **включённой
видеокарте**. Плюс три раунда войны версий, и каждый давал не ошибку, а **молча
неверный результат**: torch под CUDA 13 на драйвере 12.4 свалился на процессор,
и замер показал 7.9 с там, где карта делает 0.06 с. Отсюда два правила,
зашитые теперь в [eval/selfhosted/setup_pod.sh](../eval/selfhosted/setup_pod.sh):
версии прибиты, и скрипт **падает**, если CUDA не видна. Ставить зависимости
на арендованной карте нельзя — образ собирается на бесплатных раннерах GitHub
([Alex011082/whisperlivekit-ruhe](https://github.com/Alex011082/whisperlivekit-ruhe)).

**Не измерено:** сколько миллисекунд даёт WhisperLiveKit. Ровно то, ради чего
арендовалась карта — деньги кончились раньше. Локальная попытка на M1 дала
недостоверные числа (разброс 2400/5100/6500 мс на одной записи, перевод не
запустился вовсе), но нашла два подводных камня, экономящих время при повторе:
нужен флаг `--pcm-input`, а перевод приходит полем `buffer_translation`, не в
строках.

**Полные замеры всех вендоров — [eval/vendor-latency-bakeoff.md](../eval/vendor-latency-bakeoff.md).**
Ключевое оттуда: **Gemini Live Translate дал 3849 мс против наших 4045** — то
есть схлопывание трёх вендоров в одну модель ничего не даёт, секунды сидят не в
сетевых прыжках, а в необходимости дослушать речь. **У Palabra 93 голоса и ни
одного ивритского** — отсюда их американский акцент, неустранимый. **Cartesia
остаётся единственным вендором, где русская запись говорит на иврите
убедительно**, и это установлено перебором, а не привычкой.

## 11.1 План по задержке (принят 26.08.2026)

Четыре шага в порядке «сначала бесплатное». Идея шагов 3–4 — основателя;
проверка литературы показала, что **обе уже реализованы в чужих работах**,
ссылки ниже. Разбор вендоров, из которого это выросло, —
[eval/vendor-latency-bakeoff.md](../eval/vendor-latency-bakeoff.md).

**Бюджет — пересчитан 26.08.2026 по всем логам сервера** (24 звонка, 85 реплик,
51 без ошибок), медианы:

| Отрезок | мс |
|---|---|
| начало речи → первая гипотеза STT | **1149** |
| первая гипотеза → коммит | **1095** |
| коммит → перевод готов | **1008** (из них у вендора 770) |
| перевод → первый звук | **240** |
| **итого до первого звука** | **3933** |

**Поправка к прежней записи.** Раньше здесь стояло «ожидание конца фразы нашим
чанкером 1318 мс». Это было неверно: `first_partial_to_commit` включает время,
пока человек **продолжает говорить**, и списывать его на нашу политику коммита
нельзя. При `max_silence_ms=300` и таком же endpointing у Deepgram собственное
ожидание чанкера — около **300 мс**, а не 1318. Значит чанкер даёт десятые доли
секунды, а секунды лежат в **распознавании (1149)** и **переводе (1008)**.

**Шаг 1. Чанкер — сделано 26.08.2026.** Не ускорение, а починка мёртвого кода.
Замер: медиана реплики **2 слова**, максимум 11, и порог `min_words=8` за 85
реплик **не сработал ни разу** — 54 из 85 единиц уходили на перевод только по
`final` от вендора, 22 по тишине, 9 по клаузе. Сделано:
- `min_words` 8 → **5**, `weak_boundary_min_words` 4 → **3**;
- **тишина считается подтверждением** (`chunker._adopt_hypothesis`).
  LocalAgreement придерживает слово, пока его не повторит вторая гипотеза, — но
  последнее слово короткой реплики видно ровно один раз и не стабилизируется
  никогда, поэтому единица ждала вендорского `final` вместо нашей тишины.
  Вендор, молчащий 300 мс, ничего уже не перепишет.

Проверка эффекта — на звонке 26.08 ([eval/call-script-2026-08-26.md](../eval/call-script-2026-08-26.md)):
ждём роста `min_words` и `clause` за счёт `final`.

**Шаг 2. Перекрыть стадии.** Сейчас цепочка последовательная и четыре стадии
складываются в сумму. Первый кусок должен озвучиваться, пока второй
переводится. Полностью инкрементальные каскады ASR→MT→TTS дают **ear-voice
span ≈3 с**, современный потоковый синтез — **75–200 мс до первого звука**.
Дни работы, ноль денег. *(Замечание основателя: предлагалось ещё 25.08, не
сделано — гонялись за вендором, который решит всё сразу.)*

**Шаг 3. Спекуляция на неуверенных местах.** Предсказывать несколько
продолжений фразы, переводить и синтезировать их заранее, отсеивать по
приходящему звуку, играть подтвердившееся. Тогда перевод и синтез исчезают из
наблюдаемого времени.

Что известно из чужих замеров:
- **TAF** (NAACL 2025) — ровно эта схема для текста: LLM сэмплирует несколько
  продолжений, каждое переводится, победитель выбирается **голосованием**, и
  политика пишет, только если согласие выше порога. **+5 BLEU при той же
  задержке** (AL = 3 слова) на De-En, En-Zh, Zh-En, En-Ja. **Иврита в списке
  нет** — на нашей паре не проверял никто.
- **Predictive ASR** (Amazon, Interspeech 2023) — предсказание всей реплики по
  началу с предвыборкой ответа: **28% попаданий ценой +20% вычислений**. Это
  голосовой ассистент, где команды предсказуемее живого разговора, — наш
  потолок попаданий ниже.
- **Speculative pre-synthesis** в голосовых агентах: синтезированный звук
  копится в спекулятивном кэше и **сбрасывается**, если приходящий звук не
  подтвердил гипотезу.

**Ограничение, которого нет в этих работах: сказанное не отзывается.** Половина
приёмов симультанного перевода разрешает себе **переписывать уже выданное** —
субтитр можно исправить. Нам нельзя, поэтому фиксация префикса окончательна.

**Денежный риск шага 3:** Cartesia тарифицируется **посимвольно**, и каждая
непопавшая ветка — оплаченный впустую синтез. Поэтому спекулировать не по всем
веткам, а переформулировав задачу: не «что человек скажет», а **«изменит ли
хвост фразы то, что я уже готов сказать»**. В иврите это в основном род и
число, цепляющиеся за конец фразы. Порог по уверенности обязателен, иначе счёт
умножается на число веток.

**Шаг 4. Своя модель prefix-to-prefix.** Причина, по которой мы ждём конца
фразы, — Gemini обучен на **целых предложениях**. Симультанные модели
тренируют на префиксных парах (STACL и далее), и они сами знают, где
остановиться. Дообучение открытой модели (Qwen3 / Gemma) на синтетике: берём
параллельный корпус RU-HE, рубим на префиксы, сильной моделью размечаем
безопасную часть перевода. Недели, постоянно горячая карта, дефицит ивритских
данных. Это тот же маховик, что заложен под анонимизированные архивы (§12), —
но заряжается раньше, чем пойдут живые звонки.

**Потолок, который не берётся ничем:** секунду-полторы речи надо услышать
физически. Живой синхронист отстаёт на те же 2–4 с. Реалистичная цель —
**2–2.5 с**, а не 0.5.

**Каждый шаг мерить.** Правило после истории с арендой карты вслепую: без
замера до и после шаг не считается сделанным.

## 11.2 Онбординг голоса: 3-4 образца, а не один (решено 28.08.2026)

**Решение основателя.** При регистрации, если пользователь хочет звучать своим
голосом, просим прислать **3-4 голосовых сообщения с нашим текстом и нужной
интонацией** — чтобы синтез перенимал не только тембр, но и **манеру, привычки,
интонацию** конкретного человека.

**Почему это важнее, чем кажется, и почему одного образца мало.**

Сегодняшний вердикт по звуку: «интонация везде хуёвая» — причём и на фразе
целиком, не только на склейке. Наш нынешний клон снят с `alex_ref.wav`: 23.7
секунды **ровного чтения одного текста**. Модели неоткуда узнать, как этот
человек задаёт вопрос, как возражает, как договаривает мысль. Ровный референс
даёт ровный клон — и это ровно то, что слышно.

**Отсюда требование к образцам: они должны различаться ПРОСОДИЕЙ, а не
длиной.** Четыре записи одного и того же ровного тона не лучше одной. Нужны
разные интонационные контуры:

| # | что просим прочитать | зачем |
|---|---|---|
| 1 | утверждение, спокойно | база тембра |
| 2 | **вопрос** | восходящий контур — его в ровном чтении нет вообще |
| 3 | короткая эмоциональная реплика (удивление, возражение) | динамика |
| 4 | длинная фраза с запятыми | как человек ведёт и завершает мысль |

**Связь с платной фичей.** Кросс-языковое клонирование не работает нигде (§10):
русский референс + ивритский синтез = сломанный голос. Отсюда решение просить
запись **на целевом языке** и продавать это. Теперь оно усиливается: просим не
один текст, а четыре, и не «прочитай», а «прочитай вот так».

**Что это НЕ отменяет.** Акцент остаётся — и остаётся фичей: так человек и
звучал бы, выучив язык. Речь про интонацию, а не про произношение.

**Инвариант не нарушается.** Присланные образцы — это данные для клонирования
голоса, а не архив разговоров. Правило «голос не хранится» (§12) касается
**записей звонков**; референс пользователь присылает сам, осознанно и ради
конкретной услуги. Но хранение референсов требует собственного согласия и
собственного срока — это отдельный пункт условий, и его надо написать до
первого живого пользователя.

## 12. Открытые риски и вопросы

- **Название:** «SameVoice» голым словом уязвимо к genericness; TESS/EUIPO не проверены напрямую.
- **Транспорт до AI-вендоров:** Cartesia — CloudFront в Тель-Авиве, но origin ~159 мс; недокументированный `api-eu.cartesia.ai` не подтверждён.
- **Deepgram EU endpoint**: ключ валиден (management API на `api.deepgram.com` отвечает 200), но сам `api.eu.deepgram.com` на живом распознавании ещё не проверен — management-эндпоинт `/v1/projects` там отдаёт 404, что нормально, однако подтверждения работы `/v1/listen` через EU-хост пока нет. Если первый звонок даст ошибку STT — временно переключить `DEEPGRAM_BASE_URL` на `https://api.deepgram.com/v1/listen` и перезамерить.
- **Голос привязан к языку вывода, а не к говорящему** (`providers/tts_cartesia.py`: словарь `self._voices` с ключами `ru`/`he`). Для звонка двух человек, где каждый говорит только на своём языке, это даёт верный результат — но случайно, а не по устройству. В общем случае (двое русскоязычных звонят одному ивритоговорящему) оба выйдут одним и тем же ивритским голосом, и обещание «твой голос на чужом языке» сломается. Правильная модель — голос на **говорящего**, из карточки участника. Переделывать до тестов не нужно, но это архитектурный долг, а не мелочь.
- **Асимметрия вечернего теста:** тестировщица услышит настоящий клон голоса основателя, а основатель услышит голос Ellen вместо её собственного — её голос не клонирован, референса нет. Лечится 20–30 секундами её записи.
- **Огласовки (никуд) в выводе Gemini:** модель возвращает иврит с огласовками (`הֵי, אֲנִי שׁוֹמֵעַ…`). Cartesia синтезирует и такой текст, и без них, но длительность выходит разной (2.7 с против 3.0 с на одной фразе) — то есть огласовки влияют на просодию. Решение, снимать ли их перед синтезом, ждёт вердикта тестировщицы на слух.
- **VoxCPM2 в потоковом режиме** не тестировался вовсе — только batch `generate()`.
- **Телефон нельзя поднести к уху — ограничение веба, не наш баг.** Звонок 26.08.2026 (Майя + Омри) провалился на этом: она держала телефон у уха и не слышала **ничего**, звук всё это время шёл из **нижнего** динамика. Проверено основателем на её аппарате руками.

  **Причина не чинится кодом.** У веба нет API, чтобы занять разговорный динамик у уха: страница в браузере играет как медиа, то есть в громкий динамик. Ни `setSinkId`, ни ограничения `getUserMedia` этого не меняют на Android.

  **Что сделано 27.08.2026:** на сенсорных устройствах при входе в звонок показывается предупреждение — «звук идёт в громкий динамик, держите телефон перед собой или наденьте наушники», один раз, с запоминанием. Это честное лечение симптома, а не причины.

  **Что из этого следует для продукта.** Приложение выглядит как телефон, и человек ведёт себя с ним как с телефоном — подносит к уху. Значит либо SameVoice сознательно объявляется **гарнитурным / громкой связи** продуктом (и тогда UI должен говорить это с первого экрана), либо нужна **нативная обёртка**: нативное приложение может запросить режим голосового вызова и разговорный динамик. Это первый по-настоящему сильный аргумент за нативный клиент — сильнее, чем push и фоновые звонки.

- **Двусторонняя проблема «оба должны поставить приложение»** — не решена архитектурно, PSTN отложен до после MVP.
- **Приватность разговоров:** израильская Поправка 13, EDPB-гранулярность согласия на использование данных для обучения — учтено в дизайне (три потока: live processing / telemetry / improvement dataset с opt-in), **в коде не реализовано**.

  **Решение основателя (25.08.2026), после появления архива звонков:** архив остаётся, но сохраняется **только при явном согласии пользователя**, который прочитал условия и поставил галочку. В условиях пишется правда: где хранится, как, зачем и сколько времени. На бесплатных тарифах согласие требуется по умолчанию; на платных его можно отключить или отредактировать условия. Сильно обезличенные архивы предназначены для обучения собственной LLM **на отдельном сервере**.

  **Разрыв между этим решением и кодом, который надо закрыть до первого настоящего пользователя:** сейчас в бэкенде **ноль упоминаний согласия** — `archive.put()` вызывается для каждого завершённого звонка безусловно. Пока участников трое и все всё знают, это неопасно; но такая вещь тихо доезжает до прода вместе со всем остальным.

  **Двух согласий, а не одного.** Хранение истории звонков для самого пользователя и обучение модели на его разговорах — **разные цели обработки**. Склеивать их в одну галочку — ровно то, что EDPB не принимает, и это уже записано в [00-concept.md](00-concept.md) как поток C с отдельным opt-in. То есть план основателя ложится на существующий дизайн, но требует двух независимых флагов: «хранить мою историю» и «использовать для улучшения переводов».

  **ГОЛОС НЕ ХРАНИТСЯ — решено 25.08.2026, инвариант продукта.** Хранятся только расшифровки, и только для улучшения обработки и перевода. В условиях использования это будет выделено **жирным**. Причина, по которой это правильное решение: текст обезличить можно, голос — нет, тембр и есть идентификатор, то есть биометрия; отказавшись от аудио, продукт снимает самую тяжёлую часть проблемы целиком, а не смягчает её.

  **Проверено в коде 25.08.2026 — обещание сейчас выполняется:** ни один путь не пишет аудио на диск, LiveKit egress не запускается нигде. Персистится ровно две вещи, обе текстовые: архив звонка (метаданные — кто, когда, языки, длительность) и eval-лог `logs/calls/*.jsonl` (оригинал и перевод). Паттерны `recordings/`, `*.ogg`, `*.ivf` в `.gitignore` оставлены как страховка на случай локальной отладки с egress — включать его в проде значит нарушить условия.
