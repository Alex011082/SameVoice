This file is the stop/go checklist for the first paid 2 x RTX 4090 SameVoice R&D session. The Pod should stay undeployed until the **pre-GPU** gates are green.

## Green now

- [x] SpeakEasy/SameVoice runtime source is in `main`.
- [x] Backend/web/Python dependencies have lockfiles.
- [x] `npm ci` + `uv sync --frozen` are used for reproducible container installs.
- [x] Source smoke tests pass in GitHub CI.
- [x] Backend and web production builds pass in GitHub CI.
- [x] RunPod shell entrypoints pass syntax validation.
- [x] CUDA-based `Dockerfile.runpod` builds successfully in GitHub Actions.
- [x] Built image boots with the keyless mock provider trio.
- [x] Web, backend and agent healthchecks pass inside the built container.
- [x] Persistent runtime layout is defined under `/workspace`.
- [x] GPU service split is defined: GPU 0 = THINK, GPU 1 = SPEAK.
- [x] Secrets/raw audio/voice embeddings/model weights are excluded from the image/repository path.
- [x] First local predictor model selected and pinned: `Qwen/Qwen3-0.6B-Base` in `gpu/model_manifest.toml:53`, wired at `docker/runpod-gpu.env.example:63`.
- [x] Predictor request/response contract defined and implemented: `gpu/predictor/app.py`.
- [x] Rolling next-source-word Top-K predictor service implemented: `gpu/predictor/app.py`, shadow-mode consumer in `agent/src/speakeasy_agent/speculation.py`, documented in `docs/10-predictor-shadow.md`.
- [x] Acoustic evidence/pruning service contract implemented: `gpu/acoustic/prune_app.py` + `gpu/acoustic/pruner.py`, documented in `docs/11-acoustic-pruning.md`.
- [x] First local MT models selected and pinned: `Helsinki-NLP/opus-mt-ru-he` and `Helsinki-NLP/opus-mt-he-ru` in `gpu/model_manifest.toml:62,71`.
- [x] The `runpod` MT stub is gone. `agent/src/speakeasy_agent/providers/mt_runpod.py` is a real HTTP client; its `POST <base>/v1/translate` body matches `TranslateRequest` at `gpu/mt/app.py:28-31` field for field.
- [x] First local TTS path chosen per language and pinned: `ResembleAI/chatterbox` in `gpu/model_manifest.toml:89`, served by `gpu/tts/app.py`. Hebrew coverage is **not** assumed — see the open blocker on a live Hebrew TTS check.
- [x] The `runpod` TTS stub is gone. `agent/src/speakeasy_agent/providers/tts_runpod.py` is a real HTTP client; every header it reads is emitted by `gpu/tts/app.py:163-171`, and both sides carry raw s16le mono.
- [x] Local experimental STT path exists alongside Deepgram: `gpu/acoustic/app.py` (websocket at `/v1/stream`) + `agent/src/speakeasy_agent/providers/stt_runpod.py`, models pinned at `gpu/model_manifest.toml:8,17`. Both sides agree on 16 kHz mono s16le and on the same six event types (`gpu/acoustic/protocol.py:13` vs `stt_runpod.py:146-153`).

The three adapters were re-read field by field against the three services. No URL path, JSON field name, header name, event type, sample rate or language literal disagrees. What is **not** aligned is behaviour at the edges, and that is what the blockers below now describe.

## Pre-GPU blockers

Ordered by what would burn paid GPU time first.

- [ ] Fix `scripts/runpod-warmup.sh:29`. `body="${3:-{}}"` ends the expansion at the first `}`, so every supplied body ships a trailing brace: passing `{"lang":"ru"}` sends `{"lang":"ru"}}`. That is the exact call made at lines 49/50/54/55, `WarmupRequest` (`gpu/acoustic/app.py:42-43`, `gpu/acoustic/prune_app.py:31-32`) rejects it with 422, `curl -fsS` fails and `set -euo pipefail` aborts the script — so acoustic never warms, local MT never warms, and the closing `nvidia-smi` never runs. Reproduced in bash 3.2 and zsh. `scripts/runpod-session.sh` calls this script at its acceptance step 5, so the one-command scenario dies here too (it now refuses to start the warmup at all when an acoustic engine is enabled and this line is still unfixed). `bash -n` (`.github/workflows/ci.yml:68`) cannot see this class of bug; add a CPU-only test that runs the script against stub `/healthz` + `/v1/warmup` apps.
- [ ] Add per-stage queue-wait and `t0..t9` instrumentation to the benchmark record. Today `UnitMetrics.stage_timings()` (`agent/src/speakeasy_agent/direction.py:99-110`) exports 7 deltas and zero absolute timestamps, so `t0..t9` cannot be reconstructed from any log. Concretely: stamp the first inbound frame (`direction.py:278`) for `t1`; split the single `first_audio` stamp (`direction.py:475-476`) into TTS-chunk arrival and sink hand-off for `t7`/`t8`; emit `_Attempt.requested_at`/`completed_at` (`speculation.py:163-164`) into the shadow record for `t3`/`t4`; add `queue_wait_ms` to `AcousticEvent` (`gpu/acoustic/protocol.py:20-28`) so the value already computed at `gpu/acoustic/engines.py:124,196` reaches the wire instead of being discarded. Point by point — what each of `t0..t9` means physically, which JSONL field carries it today, where the anchor is wrong and what may therefore not be claimed from the current log — is written out in `docs/12-latency-timestamps.md`.
- [ ] Give the server-reported latencies a path into the eval log. `last_server_latency_ms` is parsed by all three adapters (`mt_runpod.py:66`, `tts_runpod.py:89`, `stt_runpod.py:165-167`), `last_server_load_ms` by MT and TTS (`mt_runpod.py:67`, `tts_runpod.py:90`) and `last_engine` by STT (`stt_runpod.py:146-149`) — and all of them are read by nothing outside `providers/` and the adapter tests. `SttEvent` (`providers/base.py:36-42`) and `TtsChunk` (`providers/base.py:102-106`) need timing fields before "engine-only latency" can ever appear per utterance.
- [ ] Finish the one-command post-boot scenario. It now exists in the working tree: `scripts/runpod-session.sh` runs preflight -> workspace-mount assertion -> engine-set check -> warmup -> GPU placement -> call test -> benchmarks -> export, exports even when a step above failed, tees every child's output into `$BENCHMARK_DIR/sessions/<run id>/session.log`, writes `session-manifest.json` next to it (git SHA, image tag, GPU inventory, enabled engines, placement verdict) and ends on a STOP-THE-POD banner; `--dry-run` validates the plan without touching a GPU. What is still open around it: the file is uncommitted and mode 644, absent from the `chmod` line at `Dockerfile.runpod:96` (so `bash <path>` is the only invocation) and absent from the `bash -n` list at `.github/workflows/ci.yml:65-68`; and its acceptance step 5 calls the still-broken `runpod-warmup.sh` (it refuses to run it when an acoustic engine is enabled, rather than posting the malformed body). The gaps it cannot paper over: `scripts/runpod-stage1-bench.py` still covers only predictor (:8101) and MT (:8103) and records no queue wait and no TTFA; `npm run demo:pipeline` builds its providers from `Config.from_env()` (`agent/scripts/mock_pipeline_demo.py:147`), so it is only mock-only when the environment says so — the session runner therefore pins `STT_PROVIDER=MT_PROVIDER=TTS_PROVIDER=mock` for that step, and with that pin it never touches ports 8101-8105 or a vendor account; `npm run smoke` exits at `scripts/check-env.mjs` because a real Pod has no repo-root `.env`; both bench scripts are mode 644 and also absent from `Dockerfile.runpod:96`; and `gpu/README.md:67` / `docs/11-acoustic-pruning.md:42` still show a bare `python …` invocation that no layer of `Dockerfile.runpod` installs — pin `/opt/venvs/think/bin/python …` there.
- [ ] Make `stt_runpod.py:151-152` distinguish fatal from recoverable server errors. The server treats an `error` event as per-utterance and keeps the session alive — at `gpu/acoustic/app.py:304` it emits `error` and still emits `speech_end` — but the adapter raises `ProviderError` on any error event, which ends the generator and makes `direction.py:345-347` exit the STT loop for the rest of the call. One failed Hebrew partial permanently deafens that direction. Either add a severity/fatal field to `AcousticEvent` or log-and-continue for errors followed by `speech_end`.
- [ ] Bound the VAD pool wait. `VAD_POOL_SIZE` defaults to 2 (`gpu/acoustic/app.py:36`), the websocket is accepted at `:423`, and only then does `acquire_iterator` block on an untimed `await self._available.get()` (`:95-99`). One call uses both slots (one session per direction), so a second concurrent call is accepted, gets its `start` message read, and then silently never receives `ready`. The client cannot notice: `ClientTimeout(total=None, ...)` at `stt_runpod.py:194` and no read deadline. Add a server-side acquire timeout that closes with an explicit error event, raise `VAD_POOL_SIZE` to 2x expected concurrent calls, and add a first-event deadline on the client.
- [ ] Call `/v1/warmup` from the agent, or make the first request survive a cold model. MT's client deadline is 4.0 s (`mt_runpod.py:24`) and TTS's is 30.0 s (`tts_runpod.py:31`), but both servers load models inside the request path (`gpu/mt/app.py:115`, `gpu/tts/app.py:89`) and report the cost as `load_ms` — a field that can only be non-zero on a request the client has already abandoned. The warmup endpoints exist (`gpu/mt/app.py:184`, `gpu/tts/app.py:142`, `gpu/acoustic/app.py:395`) and nothing in `agent/src` calls them; only the operator script does.
- [ ] Move the synchronous GPU work off the event loop. Silero VAD runs inline at `gpu/acoustic/app.py:185` and Nemotron mel extraction at `:231,239` -> `engines.py:222-246`, while only the Hebrew path is offloaded via `asyncio.to_thread` (`:266`). A stalled loop is not degraded service on the client side, it is a hard stop: the 500-frame queue raises `ProviderError` (`stt_runpod.py:79-82`), which `direction.py:283-290` turns into `_input_dead=True`, and the 15 s heartbeat (`stt_runpod.py:208`) tears the socket down anyway.
- [ ] Make `config.py:212-214` read `LOCAL_MT_URL`/`LOCAL_TTS_URL`, or stop advertising them. The dormant-URL guards tell the operator the provider activates on "`RUNPOD_MT_URL` or `LOCAL_MT_URL`" (`mt_runpod.py:38`, `tts_runpod.py:46`), but only the `RUNPOD_*` names are read, while `docker/runpod.env.example:48-49` and `.env.example:420-421` set only the `LOCAL_*` names. In those profiles `MT_PROVIDER=runpod` raises the stub `NotImplementedError` against a live service.
- [ ] Resolve the TTS profile footgun: `docker/runpod-gpu.env.example:27` leaves `LOCAL_TTS_CMD` empty so the service is never started by `docker/entrypoint.sh:109`, while `:36` still sets `RUNPOD_TTS_URL=http://127.0.0.1:8104`. Selecting `TTS_PROVIDER=runpod` there yields a per-unit connection-refused error instead of the clear "not configured" error. Comment the URL out, or point the operator at `docker/runpod-gpu-tts-ab.env.example:21`, which is the only profile that actually starts `gpu/tts/app.py`.
- [ ] Make `scripts/runpod-preflight.sh` prove `/workspace` is a mount, not just writable. Lines 27-42 only `mkdir` and write a temp file, and `df -h` at :46 is printed without being asserted — an unattached volume prints "persistent workspace is writable" and `PASS preflight`. Compare `stat -c %d /workspace` against `/` (or read `/proc/mounts`) and fail, plus assert a minimum free space.
- [ ] Land the export path that now exists in the working tree, instead of deciding one. `scripts/runpod-export.sh` implements it: it refuses to write when its destination shares a device id with `/` (container disk, which `runpod-preflight.sh`'s writability test cannot tell apart), collects by extension allow-list so raw audio, embeddings and weights cannot leave, names every skipped file in `EXCLUDED.txt`, writes a `.partial` tarball first, and prints the `scp` / `rsync` pull line (plus `runpodctl send` when that binary is present). `docs/RUNPOD_RND.md:108-118` documents it. What is still open: it is uncommitted and, although it is already mode 755 in the working tree, still absent from the `chmod` line at `Dockerfile.runpod:96` and from the `bash -n` list at `.github/workflows/ci.yml:65-68`. Independent of it: make `scripts/runpod-stage1-bench.py:140-145` write incrementally instead of once at the end, default `--output` on `scripts/acoustic-pruning-bench.py:83`, and give `agent/scripts/summarize_prediction_shadow.py:118-126` — still stdout-only, and not one of the steps the session runner tees — a file destination under `$BENCHMARK_DIR`.
- [ ] Fix the env-var propagation that makes preflight pass silently. Every engine/venv check at `scripts/runpod-preflight.sh:55-121` is gated on `*_CMD` being set in the calling shell, but those may live in `/workspace/config/samevoice.env`, which only `docker/entrypoint.sh:20-26` sources. An interactive shell therefore skips all checks and still prints `PASS preflight`. Have preflight and warmup source `$SAMEVOICE_CONFIG_FILE` themselves, or fail when zero engines are enabled.

## Что уже проверено замерами, а не предположениями

Три дня замеров лежат в репозитории на ветке `docs/session-findings` (в рабочем дереве `work/gpu-glue` каталога `eval/` нет — читать через `git show docs/session-findings:<путь>`). **Эти вопросы закрыты. Не переоткрывать их на платном GPU.**

- **Своё железо оказалось МЕДЛЕННЕЕ облака** — `eval/vendor-latency-bakeoff.md`. Замер на NVIDIA L4 (24 ГБ, драйвер 580, torch 2.9+cu129, GCP `europe-west4-b`), карта заведомо сильнее тель-авивской T4, то есть это верхняя граница. Речь → первый текст: **1590 мс** против **917 мс** у Deepgram. Речь → первый перевод: **3647 мс** против **2095 мс** у связки Deepgram+чанкер+Gemini. Модель была уже прогрета, то есть числу дана фора. Гипотеза «свой GPU уберёт вендорские прыжки и даст выигрыш в секунды» **опровергнута замером**. Отсюда и рамка первой платной сессии: она про инфраструктуру и инструментовку, а не про то, чтобы обогнать облако.
- **Инкрементальный перевод уже работает — на вендорской модели и без обучения** — `eval/mt/INCREMENTAL.md`, скрипт `eval/mt/bench_incremental.py`. Перевод впервые выдаётся на **50%** фразы, к концу реплики готово **80%**; вызовов модели в **4.6 раза** больше при задержке одного вызова 558 мс. Рабочей оказалась третья редакция промпта: модели дают источник на текущий момент и уже произнесённое вслух и просят **только продолжение** — переписать сказанное она не может не по просьбе, а по построению интерфейса. Покупать сервер и дообучать модель ради этого **не требуется**.
- **Задержка структурная, а не языковая** — `eval/langs/RESULT.md`. Английский против русского по времени до первой гипотезы: разница **1 мс**. Значит гипотеза «наши секунды от того, что русский и иврит хуже обслужены» неверна. Там же: у иврита задержка сопоставима, а **точность — нет** (дважды распознавание теряло слова), и это отдельная проблема.
- **Около 300 мс «неизбежной» секунды были нашей настройкой** — `eval/langs/RESULT.md`, таблица по `endpointing`: 300 (стояло у нас) → **980 мс** до первой гипотезы, 100 → **678 мс**, 50 → **580 мс**.
- **Выбор модели перевода сделан по замеру, а не по вкусу** — `agent/src/speakeasy_agent/config.py:124-134`, прямо в этом дереве. На 24 реальных репликах из живых звонков: `gemini-3.7-flash` — медиана 1133 мс, **3 отказа из 24**; `gemini-3.5-flash-lite` — медиана **635 мс, 0 отказов из 24**. Ошибка рода у flash-lite закрылась примером в промпте, а не правилом.

Практическое следствие для первой сессии: единственная причина платить за GPU — получить числа, которых сейчас нет (queue wait, `t0..t9`, VRAM, TTFA). Всё, что уже измерено выше, повторного замера не требует.

## First paid session acceptance test

The first Pod session is infrastructure validation, not a latency claim. Before loading large models:

1. choose the smallest local engine(s) **before** the Pod boots and set the matching `*_CMD` values in the Pod environment — `docker/entrypoint.sh:105-109` starts engines only at container boot, so this cannot be done after step 3. A `*_CMD` pointing at an absent venv kills the child, `wait -n` returns and the container restart-loops (`docker/entrypoint.sh:132-143`) before any check can name the cause;
2. obtain a shell on the running container and `source "${SAMEVOICE_CONFIG_FILE:-/workspace/config/samevoice.env}"` — without it preflight skips every engine check and still prints `PASS`. Document the exact access path (RunPod web terminal / SSH); the image entrypoint is tini plus a supervisor, with no sshd and no shell mode;
3. run `/opt/samevoice/scripts/runpod-preflight.sh` and verify both GPUs;
4. confirm `/workspace` is a real mounted volume, not merely writable, and record which storage class it is — a Pod volume survives stop/start but not terminate, and only a network volume survives termination;
5. run `bash /opt/samevoice/scripts/runpod-warmup.sh` (only after the `body` bug above is fixed) and capture per-GPU `memory.used` around each warmup — this is currently the only real evidence of GPU 0 / GPU 1 process placement, because `nvidia-smi` inside a container generally cannot attribute processes and `runpod-preflight.sh:111-113` only prints the intended split from env;
6. run the post-boot benchmark scenario and record GPU memory, queue wait, provider TTFA/latency and end-to-end timestamps. Steps 5-6 are only worth paying for once the instrumentation blocker above is closed; without it the numbers cannot be attributed to a stage;
7. export the artifacts off the Pod **before** stopping it (`bash /opt/samevoice/scripts/runpod-export.sh`), with a run manifest next to them (GPU model/driver, image tag/digest, git SHA, enabled engines, env profile) so a recovered JSON can be attributed to a configuration afterwards;
8. stop the Pod as soon as the planned experiment is complete — **and just as fast when any step above fails**. A failed session bills at the same rate as a successful one, the restart-loop from step 1 bills indefinitely while nothing works, and nothing in this repository stops a Pod: the last human instruction on the screen is the only thing that does. Export first (step 7 runs on the failure path too), then stop.

Steps 3-8 are what `scripts/runpod-session.sh` chains in one command, including the export on the failure path; run it as `bash /opt/samevoice/scripts/runpod-session.sh` (it is not on the image's `chmod +x` line) and `--dry-run` it first. Doing them by hand is still valid — the numbering above is the contract, the script is one implementation of it.

## Rule

Do not spend paid GPU time discovering package names, dependency conflicts, missing environment variables or container boot problems. Those belong in GitHub CI or a CPU-only build environment first.
