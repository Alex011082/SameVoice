# Корпус для replay-бенчмарка: протокол записи и разметки

Два сценария чтения в этом каталоге — [ru-recording-script.md](ru-recording-script.md)
и [he-recording-script.md](he-recording-script.md) — это ещё **не** датасет.
Датасет получается, когда к каждой строке сценария добавлены запись, физический
онсет целевого слова и честная точка стабилизации обычного STT.

**Записей нет ни одной — не снято.** В каталоге лежит только текст. Пока записи
нет, приёмка сессии (ниже) невыполнима для обоих языков, а гейт без ивритской
половины даёт HOLD (`LANGS = ("ru", "he")` в
`agent/src/speakeasy_agent/benchmark_gate.py`, обе строки обязательны).
Этот файл описывает, как записи получить, и — что важнее — какие три вещи на
записи молча завышают результат.

**Контракт задан не здесь.** Поля манифеста описаны в
[../../docs/10-acoustic-replay-benchmark.md](../../docs/10-acoustic-replay-benchmark.md)
и образец лежит в
[../../docs/acoustic-replay-manifest.example.json](../../docs/acoustic-replay-manifest.example.json).
Всё ниже существует только затем, чтобы эти поля можно было заполнить, не
соврав.

Одна строка сценария → один элемент манифеста:

| откуда | поле |
|---|---|
| сценарий | `lang`, `prefix`, `truth`, `contextTerms` |
| запись | `wav`, `id` |
| выравнивание | `wordStartMs` |
| отдельный прогон STT | `baselineSttStableMs` |
| только живой shadow-прогон | `predictorReadyMsFromWordOnset` (необязательное) |

## Что это за записи и чего с ними нельзя делать

**Это речь живых людей, записанная с их согласия, ради одного замера.** Не
архив звонков, не обучающая выборка, не референс для клонирования голоса.

1. **Согласие берётся до записи, письменно, и хранится вне git и вне пода.**
   Участник до начала знает: что записывается, зачем, где будет лежать, как
   долго и что запись не уходит ни одному вендору — весь бенчмарк идёт на
   локальных моделях из `gpu/model_manifest.toml`.
2. **Согласие на бенчмарк — не согласие на обучение.** Дообучение или
   файн-тюн на этих записях требует отдельного согласия. Механизма согласий в
   коде нет — **не реализовано**; сейчас это бумага и дисциплина.
3. **Отзыв согласия удаляет элементы из корпуса.** Корпус после удаления —
   **другой корпус**. `docs/10-acoustic-replay-benchmark.md` требует сравнивать
   конфигурации на одном и том же материале, поэтому факт удаления
   записывается в `CORPUS.md` (ниже), и прошлые прогоны после этого не
   сравнимы с новыми напрямую.
4. **Диктор обозначается псевдонимным кодом** (`ru-f1`, `he-m2`), а не именем.
   Таблица «код → человек» живёт с бумагой о согласии, не в репозитории и не
   на поде.

### В git корпус не попадает

Прецедент уже есть: `eval/voice-refs/` не коммитится, и в
[../voices.md](../voices.md) правило сформулировано прямо — запись голоса это
биометрия, а история git необратима. Здесь ровно тот же случай. `.gitignore`
ловит аудио несколькими способами (`*.wav`, `*.mp3`, `*.flac`, `*.m4a`,
`audio/`, `recordings/`, `datasets/`, `consented-data/`), но **полагаться на
шаблон нельзя**: `manifest.json` под них не подпадает и закоммитится молча.

Поэтому корпус целиком (аудио + манифест) лежит **вне рабочего дерева**:

- рабочая копия на поде — `/workspace/datasets/replay/`;
- мастер-копия — на зашифрованном носителе рядом с бумагой о согласии.

В git попадает только текст: этот файл, сценарии чтения и `CORPUS.md` — реестр
сессий по образцу `eval/voices.md` (дата, язык, коды дикторов, число
пригодных элементов, метод выравнивания, id движка STT для базовой линии,
`sha256` манифеста). Реестр не биометрия, и он же делает прогоны сравнимыми.

## Запись

### Техника

| параметр | значение | почему так |
|---|---|---|
| частота | пишем 48 кГц, отдаём 16 кГц | `_load_pcm` в `scripts/acoustic-replay-bench.py` требует ровно 16000 Гц и сам не пересемплирует — файл другого формата отваливается с ошибкой |
| каналы | моно | там же: `channels != 1` — отказ |
| разрядность | s16 (16 бит) | там же: `width != 2` — отказ |
| формат | WAV PCM | читается модулем `wave`, никаких контейнеров |
| длина | одно предложение на файл | элемент манифеста адресует одно целевое слово; два предложения в файле дают два онсета и ошибку разметки |

Оригинал 48 кГц сохраняется, к бенчмарку идёт производная 16 кГц:

```bash
ffmpeg -i raw/ru-f1-007.wav -ac 1 -ar 16000 -c:a pcm_s16le audio/ru-f1-007.wav
```

Никаких `-af loudnorm`, `afftdn`, компрессоров, гейтов и эквалайзеров. Ни при
записи, ни после.

### Условия

**Телефонные условия предпочтительнее студийных.** Продукт видит гарнитуру
или микрофон телефона через WebRTC, а не конденсатор в обработанной комнате.
Корпус, записанный в студии, измерит акустический разведчик на материале,
которого в проде не бывает: чище атака, богаче верх, ровнее уровень.

Но «телефонные условия» — это тракт, а не грязь. Нельзя:

- музыка и телевизор фоном (шумодав потом всё равно запрещён);
- второй голос в комнате;
- клиппинг;
- любая пост-обработка, которую мы контролируем.

Обработка, встроенная в браузер и в сам телефон, — часть продакшн-тракта, и
её отключать не надо. Важно записать в `CORPUS.md`, какой именно тракт
использовался: два корпуса, записанные разными путями, между собой не
сравнимы.

### Дикторы

**Минимум два на язык, мужчина и женщина.** Один диктор превращает retention
на окне 50–100 мс в свойство одного речевого тракта: на таком отрезке
свидетельство — это в основном первый звук, а он у мужского и женского голоса
разный по формантам и по длительности взрыва. Результат на одном голосе
неизвестно куда обобщается.

### Именование

`id` = имя файла без расширения, и он же несёт язык и диктора:

```
{lang}-{speaker}-{NNN}
ru-f1-007   →  audio/ru-f1-007.wav
he-m2-014   →  audio/he-m2-014.wav
```

В манифесте:

```json
{
  "id": "ru-f1-007",
  "lang": "ru",
  "wav": "audio/ru-f1-007.wav",
  "speaker": "ru-f1"
}
```

Путь `wav` разрешается относительно `--dataset-root`. Совпадение `id` и имени
файла делает потерянный или лишний файл видимым глазом, без скрипта.

Поле `speaker` бенчмарк **не читает**: `_load_manifest` копирует объект
целиком, а `_run_sample` берёт только известные ключи. Разбивки метрик по
диктору в отчёте нет — **не реализовано**; поле нужно, чтобы приёмка сессии
(ниже) считалась вручную и чтобы позже эту разбивку можно было сделать не
переразмечая корпус.

## Три вещи, которых на записи быть не должно

Все три не ломают прогон. Они дают зелёный отчёт на материале, которого в
звонке не бывает.

### 1. Пауза перед целевым словом

Диктору естественно притормозить перед словом, которое ему подчеркнули в
сценарии. Именно это и нельзя.

- **Первые 50 мс становятся чистой атакой из тишины.** В живом потоке слово
  приезжает в коартикуляции с предыдущим: разведчик видит хвост предыдущего
  слова и смазанный переход. Retention, измеренный на чистой атаке, — это
  ответ на другой вопрос.
- **Пауза — это граница сегмента для VAD.** В `gpu/acoustic/app.py` перед
  целевым STT стоит Silero с `ACOUSTIC_VAD_MIN_SILENCE_MS=180`. Пауза длиннее
  этого закрывает высказывание, и `baselineSttStableMs` начинает мерить
  поведение эндпойнтера, а не скорость, с которой обычный STT утрясает слово.
- **Пауза прячет ошибку выравнивания.** На границе тишина→речь онсет находит
  кто угодно. Корпус с паузами никогда не покажет, что метод разметки плохой.

Практически: целевое слово не должно быть последним в предложении и не должно
идти после запятой.

**Существующий русский сценарий этому правилу не подчиняется, и это осознанно.**
В нём целевое слово стоит в конце в десяти строках (6, 7, 10, 14, 19, 21, 22,
25, 28, 33), а в семи строках (1, 2, 7, 8, 12, 18, 21) пауза перед целевым
словом есть в самом тексте. Обе группы там же и объявлены отдельными
подсчётами. Требование к разметке отсюда жёстче, а не мягче: эти строки нельзя
складывать в одно среднее с остальными, потому что у них граница слова заведомо
легче. Задача записи — не удлинять паузу сверх той, что есть в тексте, и не
добавлять её туда, где её нет.

### 2. Утрированная артикуляция

«Прочитай почётче» завышает результат с двух сторон одновременно.

- Различающая энергия сдвигается **раньше**: гласный полнее, взрыв смычного
  отчётливее. Именно то, что измеряют окна +50/+100 мс. Retention растёт по
  причине, которой в звонке не будет.
- Речь замедляется, слово тянется дольше, обычный STT утрясает его **позже** —
  `baselineSttStableMs` растёт, а lead считается как
  `baselineSttStableMs − readyAfterWordOnsetMs`. То есть тот же приём отдельно
  надувает и числитель преимущества.

Гейт требует p50 cold-parallel lead ≥ 150 мс
(`gpu/acoustic_gate.default.json`). Разница между обычным и «дикторским»
темпом легко даёт эти 150 мс сама по себе.

Инструкция диктору — одна фраза: **говори так, как сказал бы это по телефону
знакомому.** Не «читай», не «диктуй».

### 3. Дубль, который меняет формулировку

Переписать дубль можно — но только тот же текст. Сказал другое слово, вставил
частицу, переставил порядок — файл в брак.

Почему это опаснее, чем кажется. Если оставить запись и **подправить манифест
под сказанное**, всё формально сойдётся: `prefix` совпадёт с аудио, `truth`
совпадёт с аудио, прогон отработает. Но строки сценария подобраны так, чтобы
целевое слово было трудным — делило первые ~100 мс с другим правдоподобным
продолжением того же префикса. Спонтанная замена почти всегда даёт слово
**легче** исходного. Так трудный элемент тихо меняется на лёгкий, а
predictor recall и retention растут — и по отчёту не видно, что корпус
подменили.

Если же манифест не править, а аудио оставить, то `prefix` не соответствует
записи: предиктор получает один контекст, разведчик слушает другой. Это
измеряет уже вообще не ту систему.

## Разметка `wordStartMs`

`docs/10-acoustic-replay-benchmark.md` запрещает прямо: «the benchmark must
not silently use ordinary STT output as the word-onset ground truth».

Причина не формальная. `wordStartMs` — это нулевая точка всех окон:
`_run_sample` режет PCM с `onset_bytes` и берёт ровно `W` миллисекунд.
Систематический сдвиг метки на 30 мс сдвигает каждое окно на 30 мс — то есть
больше половины самого короткого окна (50 мс). А если онсет взят из выхода
того же STT, с которым мы потом сравниваемся, метка и базовая линия
оказываются зависимыми, и lead перестаёт что-либо значить.

### Альтернатива: принудительное выравнивание

Инструмент, который считается на CPU: **Montreal Forced Aligner (MFA)** —
Kaldi-овский выравниватель, ставится через conda
(`conda install -c conda-forge montreal-forced-aligner`), на вход берёт
16 кГц моно WAV плюс текст произнесённого, на выходе даёт TextGrid с
границами слов. Он не транскрибирует: текст мы ему даём, он ищет только
границы — поэтому это не «выход обычного STT».

**Что об MFA проверено в этом репозитории: ничего.** Он не установлен, не
заведён ни в `gpu/think-requirements.txt`, ни в `gpu/model_manifest.toml`, не
запускался ни разу. Точность на нашем материале — **не измерено**. Всё, что
написано про MFA дальше, — план, а не результат.

Два известных незакрытых вопроса, которые надо проверить **до** сессии
записи, а не поверить этому файлу:

- **Русский.** В зоопарке MFA есть акустическая модель и словарь для русского
  (`mfa model download acoustic russian_mfa`). Наличие проверить командой,
  качество на телефонном тракте — **не измерено**.
- **Иврит.** Ивритской акустической модели в зоопарке MFA, насколько известно
  на момент написания, нет. Это надо перепроверить; если её действительно
  нет, иврит идёт по запасному пути.

### Запасной путь и почему он не бесплатный

CTC-выравнивание (`torchaudio.functional.forced_align`) на тех же
wav2vec2-чекпойнтах, что уже заведены в `gpu/model_manifest.toml`
(`bond005/wav2vec2-base-ru`, `imvladikon/wav2vec2-large-xlsr-53-hebrew`),
считается на CPU и покрывает оба языка. `torch>=2.8` в
`gpu/think-requirements.txt` уже есть, **`torchaudio` — нет**, его пришлось бы
добавить отдельным решением.

Ловушка: это те же чекпойнты, что стоят в ролях `acoustic_pruner_ru` и
`acoustic_pruner_he`. Разметив онсет моделью прунера, мы ставим границу туда,
где её видит сам прунер, — и потом этой же границей его оцениваем. Замкнутый
круг ровно в том месте, которое меряется. Если этот путь используется, метод
записывается в манифест (`alignmentMethod`, поле бенчмарком игнорируется) и в
`CORPUS.md`, и результат читается как смещённый, а не как истина.

### Арбитр — рука

Ручная разметка по спектрограмме (Praat, Audacity) — единственный метод без
модельной зависимости, и он остаётся арбитром при любом автоматическом.

**Обязательная калибровка каждой сессии:** случайные 20% элементов каждого
языка размечаются вручную вслепую, и в `CORPUS.md` записывается медиана и
максимум |Δ| между ручной и автоматической меткой.

Порог **предлагается, а не измерен**: медиана |Δ| ≤ 10 мс, максимум ≤ 25 мс.
Обоснование ровно одно — самое короткое окно бенчмарка 50 мс, и ошибка в
25 мс это его половина. Если реальный разброс окажется больше, вывод не
«снизить порог», а «на окне 50 мс этот корпус ничего не измеряет».

Сомнение при ручной разметке — это брак элемента, а не «поставлю на глаз».

## `baselineSttStableMs`

Это самое манипулируемое число во всём бенчмарке. Обе проверки гейта на lead
(`leadPositiveRateMin`, `leadP50MsMin`) читают
`coldParallelLeadVsSttMs = baselineSttStableMs − (max(W, predictorRTT) + P)`,
где вклад от нас измеряется машиной, а `baselineSttStableMs` приносим мы.
Завысить его на 200 мс — значит выдать вердикт PROMOTE руками.

**Скрипта для получения этого числа в репозитории нет — не реализовано.**
`scripts/acoustic-replay-bench.py` принимает его как данность. Процедура ниже
описывает, что этот скрипт должен делать.

### Процедура

1. **Тот же самый WAV**, что лежит в манифесте, — 16 кГц моно s16, не
   оригинал 48 кГц и не другой дубль.
2. Подать его в продакшн-тракт STT: websocket `/v1/stream` сервиса на
   `127.0.0.1:8102` (`gpu/acoustic/app.py`), стартовое сообщение
   `{"type":"start","lang":"ru|he","sample_rate":16000,"channels":1}`, дальше
   бинарные кадры PCM.
3. **Подавать в реальном темпе, 1×, кадрами продакшн-размера.** Отдать файл
   целиком нельзя: тогда «время до стабильности» превращается в скорость
   декодирования, и на более быстрой GPU результат улучшится без единого
   изменения в продукте. Быстрее реального времени — база схлопывается,
   медленнее — раздувается. Только 1× соответствует звонку.
4. Логировать каждое событие `partial` и `final` со стенным временем от
   начала подачи.
5. Найти момент `T`, после которого целевое слово присутствует в гипотезе и
   **больше не меняется до конца высказывания**. Считается последнее
   изменение, а не первое появление: слово, возникшее на 300 мс и переписанное
   на 520 мс, на 300 мс стабильным не было.
6. Сравнивать формы той же нормализацией, что и бенчмарк, — `_word_key`,
   то есть `strip().casefold()`. «Купить» и «купить» это не изменение.
7. `baselineSttStableMs = T − wordStartMs`. Отсчёт от онсета слова, не от
   начала файла.

### Почему обязательно то же самое аудио

Lead — это разность двух времён, снятых с **одного физического
высказывания**. Другой дубль той же фразы тем же диктором отличается темпом,
длительностью слова, коартикуляцией и точкой онсета на десятки, а иногда и на
сотню-другую миллисекунд. Эта разница попадает в lead целиком и напрямую — а
порог гейта `leadP50MsMin` равен 150 мс. То есть вторым дублём можно
изготовить весь запас, который гейт считает доказательством гипотезы.

Дополнительно фиксируется, иначе число протухает:

- **id и ревизия движка** (`nvidia/nemotron-3.5-asr-streaming-0.6b` для ru,
  `ivrit-ai/whisper-large-v3-turbo-ct2` для he). Сменился движок — база
  недействительна, переснимать, а не переиспользовать.
- **Модель GPU.** База и replay — это оба стенные времена. База, снятая на
  одной карте, и прунер, замеренный на другой, дают lead между двумя
  машинами. Снимать в одной сессии пода; если не вышло — записать обе карты и
  считать такой lead недоверенным.

### Ограничение, специфичное для иврита

Русский идёт через Nemotron cache-aware streaming. Иврит — через
скользящие снимки ivrit.ai Whisper, и в `gpu/acoustic/app.py` они
привязаны к `ACOUSTIC_HE_PARTIAL_INTERVAL_MS=480` и
`ACOUSTIC_HE_PARTIAL_MIN_AUDIO_MS=700`.

Значит ивритская база **квантована шагом около 480 мс** и не может появиться
раньше 700 мс речи. Это не оценка, а константы кода. Ивритский lead поэтому
грубее русского по построению, и это пишется в `CORPUS.md`, а не выясняется
задним числом при чтении отчёта.

### `predictorReadyMsFromWordOnset` на записи не заполняется

Это результат живого shadow-прогона, а не свойство файла. Поля нет — бенчмарк
честно считает пессимистичный cold-parallel lead. Выдуманное отрицательное
значение не сдвинет вердикт (гейт читает cold-parallel), но подделает
`observedChainLeadVsSttMs` в отчёте. Оставлять пустым.

## Почему корпус должен содержать трудные элементы

`docs/11-acoustic-pruning.md`: прунер **переранжирует** кандидатов и никогда
их не удаляет. Отсюда `demotedBelowRate.top20` при Top-20 кандидатах
структурно около нуля — он не измеряет ничего. Смотреть надо `top5` и `top3`,
а «выбросил слово совсем» — это отдельное поле `vanishedRate`, у которого на
исправном прогоне нет структурной причины быть ненулевым вообще.

С `demotedBelowRate` есть отдельная ловушка чтения: в коде это «ранг после
переоценки ниже N», а не «слово было в Top-N и вышло», и знаменатель — все
позиции, где предиктор дал истинное слово. Поэтому цифра бывает единицей там,
где акустика улучшила всё, и нулём там, где испортила всё; рядом всегда надо
печатать `rankDelta.harmedRate`. Разобранные примеры — в
[ru-recording-script.md](ru-recording-script.md), раздел «Что считать
результатом».

Единого поля «drop rate» больше нет: `conditionalDropRate` убран из
`agent/src/speakeasy_agent/benchmark_gate.py` именно потому, что он складывал
эти два разных исхода в одно число.

Основатель называет «как часто прунинг выбрасывает правильное слово» своей
самой опасной метрикой. У неё есть второй способ выглядеть нулевой, и он
целиком в нашей власти: если все целевые слова легко различимы по первому
звуку, drop rate будет около нуля потому, что корпус лёгкий, а не потому, что
прунер безопасен. Две независимые причины нуля — и по отчёту они неотличимы.

Поэтому **не меньше трети элементов на язык должны быть трудными**: целевое
слово делит первые ~100 мс минимум с одним другим правдоподобным
продолжением того же префикса. Сценарии так и составлены. Задача записи —
не подменить их лёгкими (см. запрет на дубль с другой формулировкой) и
проследить, чтобы доля трудных элементов среди **пригодных** не просела после
отбраковки.

## Приёмка сессии

Сессия засчитывается, только если после отбраковки на **каждый** язык есть:

| требование | значение | откуда |
|---|---|---|
| пригодных целевых слов | ≥ 30 | `minSamplesPerLanguage` в `gpu/acoustic_gate.default.json` |
| дикторов | ≥ 2, мужчина и женщина | выше |
| доля одного диктора | ≤ 60% пригодных | чтобы результат не был свойством одного голоса |
| доля трудных элементов | ≥ 1/3 пригодных | выше |
| позиции в предложении | не только конец фразы | иначе меряется одна просодическая позиция |
| ручная калибровка онсета | 20% элементов, расхождение записано | выше |
| `baselineSttStableMs` | у всех элементов | без него lead не считается и PROMOTE невозможен |

Писать надо с запасом: **45–50 пригодных элементов на язык**. Считаются
элементы манифеста, а не строки сценария, и по двум языкам запас получается
очень разный:

| | строк | из них в манифесте | элементов до отбраковки |
|---|---|---|---|
| `ru` | 35 | 32 (у 1, 12, 18 пустой `prefix` — `_load_manifest` их отклонит) | **64** (оба диктора читают все) |
| `he` | 35 | 35 | **41** (29 строк привязаны к одному роду, парных всего 6) |

Ожидаемый процент брака — **не измерено**, первая сессия его и покажет. Но
арифметика запаса известна уже сейчас: **ивритская половина в норматив 45–50 не
укладывается вообще**, а порог `minSamplesPerLanguage` = 30 она держит только
при браке ниже 27%. `LANGS = ("ru", "he")`, обе строки обязательны — значит
недобор на иврите отправляет в HOLD и успешно снятую русскую половину.
Планировать сессию, считая, что «оба языка дают по 70», нельзя.

Гейт считает выборки на целевом окне отдельно от общего числа элементов, но
две его проверки ведут себя по-разному, и путать их нельзя:

- `{target} ms acoustic samples` — это `len(rows)`, то есть **все** строки окна,
  включая отвалившиеся. Элемент, у которого клип короче окна, отсюда не
  исчезает, и эта проверка недобор данных не поймает;
- `{target} ms pruner round-trip samples` считает только строки с числовым
  `roundTripMs`, то есть реально дошедшие до прунера. Вот она и просядет.

Плюс отвалившиеся строки попадают в `erroredRate`, а он входит в проверку
`Top-5 miss rate`. Итог тот же — 30 записанных элементов при нескольких
отвалившихся на окне дают HOLD по недостатку данных, — но получается он не той
проверкой, на которую смотрят первой.

### Файл непригоден, если

- после конвертации это не 16 кГц / моно / s16 — `_load_pcm` отклонит его
  целиком;
- после `wordStartMs` осталось меньше 250 мс аудио. Тогда длинные окна дают
  `audio shorter than requested word-onset window`, элемент выпадает **только
  на части окон**, и дырка в выборке не бросается в глаза;
- `wordStartMs` вышел за длительность файла (`wordStartMs is beyond WAV
  duration`) — почти всегда признак разметки не того файла;
- перед целевым словом слышна пауза;
- сказано не то, что в сценарии;
- клиппинг, посторонняя речь, музыка;
- применена любая обработка, которую мы контролируем;
- онсет не удаётся разметить уверенно.

## Где корпус живёт на поде и что с него выгружается

Рабочее размещение:

```
/workspace/datasets/replay/
├── manifest.json
└── audio/
    ├── ru-f1-007.wav
    └── he-m2-014.wav
```

Прогон (`docs/10-acoustic-replay-benchmark.md`):

```bash
cd /opt/samevoice
/opt/venvs/think/bin/python scripts/acoustic-replay-bench.py \
  --manifest /workspace/datasets/replay/manifest.json \
  --dataset-root /workspace/datasets/replay \
  --gate-config gpu/acoustic_gate.default.json \
  --output /workspace/benchmarks/acoustic-replay.json \
  --markdown /workspace/benchmarks/acoustic-replay.md
```

### Выгрузка: `scripts/runpod-export.sh` корпус НЕ забирает

Это не недоработка, а решение, записанное в самом скрипте. `${WORKSPACE}/datasets`
входит в `FORBIDDEN_ROOTS` наравне с весами моделей, голосовыми референсами и
архивом звонков; попытка указать источник экспорта внутрь этого дерева или на
его родителя останавливает скрипт с ошибкой. Плюс второй фильтр: `ALLOWED_EXT`
это `json jsonl ndjson csv tsv txt log md toml yaml yml` — `.wav` не пройдёт
даже случайно, и бандл прямо декларирует `"raw_audio_included": false`.

С пода уезжает **только отчёт**: `/workspace/benchmarks/acoustic-replay.json` и
`.md` (это `BENCH_DIR`), плюс eval-логи и манифест прогона.

Два следствия, о которых надо помнить до конца платной сессии:

1. **`manifest.json` тоже не выгружается** — он лежит внутри
   `/workspace/datasets`. Разметка, стоившая часов ручной работы, экспортом не
   спасается.
2. **Экспорт не является резервной копией корпуса.** Мастер-копия — вне пода,
   с самого начала. `docs/RUNPOD_RND.md`: под не должен быть единственной
   копией чего-либо важного.

Запускать до остановки пода:

```bash
scripts/runpod-export.sh
```

### Сверка, что реплей идёт на том же корпусе

Требование сравнивать конфигурации на одном материале ничем в коде не
обеспечено. Минимум, который работает: положить `sha256` рядом с каждым
элементом манифеста и записать `sha256` самого манифеста в `CORPUS.md`.

Манифест лишние ключи допускает — `_load_manifest` копирует объект целиком, а
читаются только известные поля. Но **бенчмарк эти суммы не проверяет** —
не реализовано; сверка руками:

```bash
shasum -a 256 /workspace/datasets/replay/audio/*.wav
shasum -a 256 /workspace/datasets/replay/manifest.json
```
