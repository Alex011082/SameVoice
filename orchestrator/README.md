# Оркестратор: брони → гнёзда → поды

Служба, которая держит обещание из [docs/19](../docs/19-scheduled-calls.md):
карта поднимается к назначенному разговору, обслуживает соседние брони без
повторного прогрева и гаснет, как только перестала быть нужна.

## Из чего состоит

| файл | что делает |
|---|---|
| `planner.cjs` | чистая раскладка броней по гнёздам. Ни сети, ни часов внутри — только вход и выход |
| `planner.test.cjs` | 12 тестов на случаи, которые обсуждались вживую |
| `notifications.cjs` | чистое расписание уведомлений: кому и когда |
| `notifications.test.cjs` | 10 тестов (запуск обоих: `node --test orchestrator/*.test.cjs`) |
| `server.cjs` | хранение броней, жизненный цикл подов, переключение агента, доставка пушей, автосозвон, HTTP-API |
| `../web/public/sv-push-sw.js` | рабочий процесс браузера: показывает уведомление, когда вкладка закрыта |
| `../web/public/sv-push.js` | подписка в приложении (кнопка «Включить уведомления») |

Почему планировщик отдельным чистым модулем: правило удержания карты —
это деньги, и его нельзя проверять «на глаз». Первая редакция правила
(«держим 10 минут») оказалась вдвое дороже простого выключения, и поймали
это арифметикой, а не наблюдением.

## Правило, которое он исполняет

Держать карту между бронями стоит `разрыв × 1.23¢/мин`; разогреть заново —
`время_прогрева × 1.23¢/мин`. Отсюда порог: **брони попадают в одно гнездо,
если разрыв между ними меньше времени прогрева плюс минута на риск.**
Сейчас порог 5 минут; со своим образом (прогрев 1.5 мин) станет 2.5.

В гнезде одновременно не больше двух пар — это замеренная ёмкость карты
(эксп. 1: при четырёх параллельных очередь угадывателя 441 мс съедает весь
наш выигрыш в 468 мс). Третья одновременная пара открывает второе гнездо и
второй под.

Новая бронь пересобирает раскладку целиком: встав между двумя гнёздами,
она может стянуть их в одно — и второй под просто не поднимется.

## API (за `x-engine-key`, наружу через `/orch/*`)

```
POST /orch/bookings            {startsAt, durationMinutes?, withUserId?, context?, autoConfirm?}
POST /orch/bookings/:id/confirm
POST /orch/bookings/:id/cancel
GET  /orch/bookings
GET  /orch/plan                — гнёзда, время прогрева, привязанные поды
GET  /orch/status              — то же плюс последние 40 строк журнала
POST /orch/reconcile           — согласовать немедленно, не дожидаясь тика
```

Согласование само крутится раз в 30 секунд: поднимает поды к началу гнёзд,
проверяет готовность, переключает агента, гасит лишнее.

## Уведомления и автосозвон

Каждый участник задаёт СВОЁ время напоминаний (`reminderMinutes`, по
умолчанию за час и за 10 минут) и флаг `autoCall`. Расписание событий брони:

| событие | кому | когда |
|---|---|---|
| приглашение | приглашённому | сразу при создании |
| подтверждение | инициатору | когда подтвердили |
| напоминание | каждому по его выбору | за N минут |
| сигнал | обоим | за 2 и за 1 минуту |
| автосозвон **или** «пора звонить» | обоим | в назначенное время |

**Автосозвон срабатывает, только если его включили ОБА.** Звонить человеку,
который на это не соглашался, нельзя — если хоть один не включил, обоим
уходит сигнал «пора», и человек нажимает сам. При автосозвоне оркестратор
создаёт звонок через боевой бэкенд (`POST /api/calls` с `ring`), и оба
снимают трубку — как соединяла телефонистка сто лет назад.

Опоздавшие события не отправляются: напоминание «за час», доехавшее через
час после разговора, только злит (окно опоздания — 5 минут). Каждое событие
шлётся один раз; отправленные помнятся в `data/sent.json`.

Доставка — веб-пуш (VAPID). Ключи лежат в `engine.env` на сервере, публичный
отдаётся приложению через `GET /orch/push/key`. Подписка человека привязана
к его `userId`; мёртвые подписки (404/410 от браузера) вычищаются сами.

## Разводка движка по звонкам

`GET /orch/engine-for?a=<userId>&b=<userId>` отвечает, какой под обслуживает
эту пару прямо сейчас. Агент спрашивает перед каждым звонком и строит
провайдеров с адресами именно этого пода — глобально ничего не
переключается, поэтому соседний разговор может идти на другой под.

Отвечаем только про **готовый** под активного гнезда. Греющийся под звонку
не поможет, а адрес мёртвого хуже молчания: агент остался бы без движка
посреди разговора. Нет ответа — звонок идёт по настройкам окружения
(обычно облако): разговор важнее оптимизации.

Со стороны агента это `agent/src/speakeasy_agent/engine_routing.py`
(12 тестов в `agent/tests/test_engine_routing.py`) и переменные
`ORCHESTRATOR_URL`, `ORCHESTRATOR_KEY`.

## Чего он пока НЕ умеет — честно

1. **Уведомления наружу.** Пуш работает только для тех, кто открыл наше
   приложение и разрешил уведомления. Собеседнику без приложения нужен
   СМС-канал — его нет.
2. **Мост «звоним обоим».** Автосозвон создаёт обычный звонок: один
   участник видит исходящий, второй — входящий. Чтобы у ОБОИХ звонило как
   входящий, нужен режим моста в бэкенде.
3. **Часовые пояса.** Время хранится в UTC; показывать каждому в его поясе
   должен интерфейс.

## Эксплуатация

```bash
node --test orchestrator/*.test.cjs          # 22 теста планировщика и расписания
systemctl status samevoice-orchestrator      # служба
journalctl -u samevoice-orchestrator -f      # что делает прямо сейчас
```

Папку тестам передавать бесполезно (`node --test orchestrator/` пытается
запустить её как модуль) — нужен шаблон имён.

Данные: `/opt/samevoice/orchestrator/data/{bookings,pods}.json` (запись через
временный файл и переименование — файл не бывает полупустым).

Параметры меняются переменными окружения службы: `ORCH_WARM_MIN`,
`ORCH_RISK_MIN`, `ORCH_CAPACITY`, `ORCH_DURATION_MIN`. После ускорения
прогрева своим образом достаточно уменьшить `ORCH_WARM_MIN` — порог
удержания пересчитается сам.

**Расширение `.cjs` обязательно**: в репозитории `package.json` объявляет
`"type": "module"`, и файл `.js` был бы разобран как ES-модуль — `require`
упал бы. На этом уже спотыкались дважды.
