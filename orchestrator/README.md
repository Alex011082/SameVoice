# Оркестратор: брони → гнёзда → поды

Служба, которая держит обещание из [docs/19](../docs/19-scheduled-calls.md):
карта поднимается к назначенному разговору, обслуживает соседние брони без
повторного прогрева и гаснет, как только перестала быть нужна.

## Из чего состоит

| файл | что делает |
|---|---|
| `planner.cjs` | чистая раскладка броней по гнёздам. Ни сети, ни часов внутри — только вход и выход |
| `planner.test.cjs` | 12 тестов на случаи, которые обсуждались вживую (запуск: `node --test orchestrator/planner.test.cjs`) |
| `server.cjs` | хранение броней, жизненный цикл подов, переключение агента, HTTP-API |

Почему планировщик отдельным чистым модулем: правило удержания карты —
это деньги, и его нельзя проверять «на глаз». Первая редакция правила
(«держим 10 минут») оказалась вдвое дороже простого выключения, и поймали
это арифметикой, а не наблюдением.

## Правило, которое он исполняет

Держать карту между бронями стоит `разрыв × 1.23¢/мин`; разогреть заново —
`время_прогрева × 1.23¢/мин`. Отсюда порог: **брони попадают в одно гнездо,
если разрыв между ними меньше времени прогрева плюс минута на риск.**
Сейчас порог 5 минут; со своим образом (прогрев 1.5 мин) станет 2.5.

В гнезде одновременно не больше двух пар — это замеренная ёмкость карты
(эксп. 1: при четырёх параллельных очередь угадывателя 441 мс съедает весь
наш выигрыш в 468 мс). Третья одновременная пара открывает второе гнездо и
второй под.

Новая бронь пересобирает раскладку целиком: встав между двумя гнёздами,
она может стянуть их в одно — и второй под просто не поднимется.

## API (за `x-engine-key`, наружу через `/orch/*`)

```
POST /orch/bookings            {startsAt, durationMinutes?, withUserId?, context?, autoConfirm?}
POST /orch/bookings/:id/confirm
POST /orch/bookings/:id/cancel
GET  /orch/bookings
GET  /orch/plan                — гнёзда, время прогрева, привязанные поды
GET  /orch/status              — то же плюс последние 40 строк журнала
POST /orch/reconcile           — согласовать немедленно, не дожидаясь тика
```

Согласование само крутится раз в 30 секунд: поднимает поды к началу гнёзд,
проверяет готовность, переключает агента, гасит лишнее.

## Чего он пока НЕ умеет — честно

1. **Два пода одновременно с живыми звонками.** Агент берёт адрес движка из
   переменных окружения, то есть в каждый момент говорит с одним подом.
   Оркестратор переключает агента на под ближайшего активного гнезда и
   пишет предупреждение в журнал, если активных гнёзд оказалось больше
   одного. Следующая работа — разводка адреса движка по звонку в
   `agent/src/speakeasy_agent/providers`.
2. **Уведомления.** Приглашение, подтверждение и напоминания в модели
   броней есть, канала доставки (СМС/пуш) — нет.
3. **Часовые пояса.** Время хранится в UTC; показывать каждому в его поясе
   должен интерфейс.

## Эксплуатация

```bash
systemctl status samevoice-orchestrator      # служба
journalctl -u samevoice-orchestrator -f      # что делает прямо сейчас
```

Данные: `/opt/samevoice/orchestrator/data/{bookings,pods}.json` (запись через
временный файл и переименование — файл не бывает полупустым).

Параметры меняются переменными окружения службы: `ORCH_WARM_MIN`,
`ORCH_RISK_MIN`, `ORCH_CAPACITY`, `ORCH_DURATION_MIN`. После ускорения
прогрева своим образом достаточно уменьшить `ORCH_WARM_MIN` — порог
удержания пересчитается сам.

**Расширение `.cjs` обязательно**: в репозитории `package.json` объявляет
`"type": "module"`, и файл `.js` был бы разобран как ES-модуль — `require`
упал бы. На этом уже спотыкались дважды.
